# Pen 1.2.14 (format 2.19): compatibility, inner shadow, background blur, lenient reading (2026-09-26)

> Trimmed 2026-09-26 for publication: observed behaviour and measurements only.

Author: Claude (Opus 5.5), leaf `MKxE6U` under `b3HCbu`, for Ben. Research only; no source changed.
Evidence files (probes, Pen exports, Woodcase renders) are in `local/MKxE6U-pen-1.2.14/` (gitignored);
reproduction commands are inline and in the appendix. Unless noted, `woodcase` is
`.build/debug/woodcase` built from `0605451`, run **with the Bash sandbox off** (see finding 9).

## Findings first

1. **Pen 1.2.14 writes format `"2.19"`.** Files it saves declare `"version": "2.19"`, and it refuses to open a file declaring any other value.
   Measured against `local/Pen-Schema-2.17.md`, the shipped schema changes in only two ways. The shadow effect loses `spread`, and there is a new
   `browser` node type. Opening an older file **rewrites every `shadowType: "inner"` to `"outer"` and deletes `spread`** in `children` and in
   `descendants` override bags — observed directly by opening a 2.17 probe file in 1.2.14 (finding 3).
2. **1.2.14 is the first Pen that draws inner shadows as inner shadows, which is why the migration exists.** `shadowType: "inner"` has been in the
   schema since 2.10 (`local/Pen-Schema.js:179`). But the 2.17 engine turned it into an outer shadow when it loaded a file. The headless 2.17 engine
   (`pen` CLI 0.3.5) re-saved our probe's three inner shadows as `"outer"`. The committed 1.2.7 reference PNG
   (`Tests/WoodcaseTests/Fixtures/render-transforms-and-effects.png`) paints the `shadow-inner` node's shadow outside its bottom-right edge, not
   inside it. The 2.19 migration converts old `"inner"` to `"outer"` so that old files keep looking the way they always did.
3. **Woodcase's round trip through 1.2.14 corrupts inner shadows today.** Any Woodcase write rewrites `version` to `"2.17"`, whatever the file said:
   `PenParser.swift:86`, `document.version = PenDocument.currentFormatVersion`. So a genuine 1.2.14 inner shadow goes out as a 2.17 inner shadow, and
   the next time 1.2.14 opens the file it migrates it to an outer shadow. Both halves were reproduced:
   - `woodcase set … kind.fills=#EE0000` on a 1.2.14-saved file changed `version` from 2.19 to 2.17 and nothing else.
   - 1.2.14 opening a 2.17 file converted all three inner shadows to outer and dropped both `spread`s. The file was saved as 2.19 (`local/MKxE6U-pen-1.2.14/app1214/probe-opened.pen`).
4. **Reading 2.19 works, with gaps; nothing crashes on the files 1.2.14 actually writes.**
   - `tree`, `get`, `set` and `render` all accept 2.19. The version gate warns and decodes with the 2.17 model (`PenParser+VersionGate.swift:80-86`).
   - That warning makes **`woodcase lint` exit 1 on every 2.19 file**, even when nothing is wrong.
   - The new `browser` node is kept verbatim as `.unknown` (`PenNode.swift:139-147`), but the layout engine gives it no size. It lays out **0×0**
     (`PenLayoutEngine.swift:409-436`), so a `fit_content` column holding a 200-high browser measured 100 instead of 310, and its later siblings moved up.
   - Three things are silently lost when Woodcase writes the file:
     - unknown keys on known node types;
     - the root-level `fonts` array, a real Pen key present in the validators of both 2.17 and 2.19 but missing from the shipped schema doc;
     - the declared version.
   - An **unknown effect `type` is fatal**. The whole file fails with exit 4, because `PenEffect`'s decoder is a closed enum (`PenEffect.swift:113-125`).
5. **Pen 1.2.14 accepts what Woodcase writes (inferred for the full count; confirmed live for one file).** Every fixture in
   `Tests/WoodcaseTests/Fixtures`, first re-written by `woodcase migrate --force`, was checked against Pen's published 2.19 validation and migration
   rules (appendix A2).
   - 78 of 79 validate clean.
   - The failure is `parser-unknown-properties.pen`, which carries a deliberate made-up node type.
   - The migration changes meaning in exactly two fixtures, and does so silently:
     - `parser-effect-variants.pen` loses one inner shadow and one spread;
     - `render-transforms-and-effects.pen` loses one inner shadow.

   Only one case in this set was confirmed by opening a file in Pen 1.2.14 itself (finding 3, section C): `probe-217.pen` came back with exactly
   these two changes. The 78/79 count across the rest of the fixtures is inferred from Pen's own rules, not spot-checked file-by-file against the
   running app.
6. **Woodcase already renders inner shadows and background blur. The brief's premise that it "only hints" at them is wrong.** The pieces already in place:
   - Model: `PenEffect.swift`.
   - CoreGraphics:
     - `PenEffectRenderer.renderInnerShadow`, which uses the inverted-path technique (`:122-175`);
     - `PenEffectRenderer.renderBackgroundBlur` (`:315-370`).
   - React:
     - `inset` in `box-shadow` (`ReactEmitter+Styles.swift:380`);
     - `backdropFilter` (`:396-402`).
   - Help: the schema help (`PenEffect+Schema.swift`).
   - Tests: `PenRendererBackgroundBlurTests`, plus blur1/2/3 MAE fixtures.

   Inner shadow matches 1.2.14 closely: the edge profile agrees to within 3/255 (finding 8). **Background blur is wrong in three ways**, and the
   MAE tests are too insensitive to notice:
   - **It composites a vertically mirrored backdrop.** A red band at y=0–50 over a 200-tall canvas shows up at y=150–200 inside a blur box
     (`local/MKxE6U-pen-1.2.14/exp/flip.pen`, at @1x and @2x). The cause is `PenEffectRenderer.swift:354-367`. After concatenating the inverse CTM,
     the context is already in y-up device space, and the extra `scaleBy(x: 1, y: -1)` flips the image.
   - **Its blur is twice as wide as Pen's.** Pen's sigma is `radius / 2`. Woodcase passes
     `radius × scale` pixels to `CIGaussianBlur`, whose radius is a sigma. Fitted over the `blur1` fixture's red/blue edge: Woodcase sigma = 10.0,
     Pen reference sigma ≈ 4.6. A 1.2.14 export at radius 20 fits sigma = 10.
   - **It blurs in linear light.** Pen blurs gamma-encoded sRGB. On the same fit, Woodcase's squared error is 0.0007 in linear light against 0.0044
     in sRGB, and Pen's is best in sRGB.
7. **Pen's background blur has two gates that Woodcase and RapidPro both ignore.**
   - **Node opacity below 1 disables it.** Pen pushes the opacity `saveLayer` before the backdrop `saveLayer`, so the backdrop it reads is the empty
     opacity layer. This was observed in both the 2.17 and the 1.2.14 exports of `probe-217.pen`: the `bg-blur-opacity` box is unblurred.
   - **A node with no fill, or a fully transparent one, shows no blur.**
     - `#FFFFFF00` and a fill-less ellipse drew nothing.
     - `#FFFFFF01` and `#FFFFFF33` blurred.

   Both gates are observed behaviour. I have not traced the second one to its code.
8. **Pen draws inner shadows at a different point in the paint order than Woodcase does.** Pen's exports show fills painted first, then inner
   shadows, then the stroke, then children. Woodcase paints fills, then the stroke, then children, then inner shadows
   (`PenRenderer.swift:385-390` pushes them as `postContent`, which runs after the children). So
   on a frame with children, or on any node with a stroke, Woodcase's inner shadow lies *over* the stroke and children, where Pen's lies under them.
   Pen's inner shadow works like this:
   - it fills the shape with the color under a `SrcOut` blend;
   - offsets the result;
   - blurs it with `MakeBlur(σ = blur/2, Decal)`;
   - draws it clipped to the shape, honouring `blendMode`.

   Measured at 1.2.14 on a 24-radius, blur-16 inner shadow, Pen's profile matches a Gaussian with σ = 8 exactly. Woodcase's CoreGraphics shadow is
   within 3/255 of it (`local/MKxE6U-pen-1.2.14/wc219/`).
9. **CoreImage fails silently inside the Claude Code Bash sandbox.** Rendered in the sandbox, `woodcase render` produced PNGs with *no* background
   blur and exited 0. With the sandbox off, the same command blurred. Every `guard … else { return }` in `PenEffectRenderer` turns a CoreImage
   failure into "no effect", so an agent checking a render in the sandbox sees a wrong picture and no error. This belongs in `gotchas.md` or
   `harness.md`, and deserves a diagnostic. I did not edit either file; the brief allowed one new document.

   > **Update (2026-09-26, leaf `Gusv9b`).** The cause is Metal, not the sandbox as such: Core Image renders through Metal even with
   > `useSoftwareRenderer`, and the sandbox leaves no Metal device, so `createCGImage` returns `nil`. The renderer's blurs now run on the CPU
   > (`PenGaussianBlur`, Accelerate) and no longer use Core Image, so there is no silent failure left to diagnose. Findings 6 and 10 are fixed
   > on the same leaf (flip, sigma `radius/2` at every scale, sRGB-space blur, capture cropped to the node), and leaf `W91Yf0` fixes finding 8's
   > paint order and draws every outer shadow.
10. **Layer blur is only right at @2x.** `renderBlur` passes the *unscaled* point radius as a pixel sigma (`PenEffectRenderer.swift:257-260`). The
    `render-transforms-and-effects` `blurred` node (radius 4) fits σ = 4 px at @1x, @2x and @3x alike. Pen's is 2 pt: 4 px at @2x, but 2 px at @1x
    and 6 px at @3x.
11. **RapidPro reads Woodcase's model directly, so two things have to change in both repos together.**
    - **The `spread` field.** RapidPro reads `PenShadowEffect.spread` and `.shadowType` directly
      (`../RapidPro/Sources/RapidPro/Conversion/PenEffect+RenderEffect.swift:13-41`), with `Package.swift:16` `.package(path: "../Woodcase")`.
      Removing `spread`, or adding an `.unknown` effect case, stops RapidPro compiling until it follows.
    - **The shared semantics that are wrong.** RapidPro already uses Pen's sigma (`radius/2`, `RapidProRenderer+Blur.swift:33-54`), but it shares
      Woodcase's other deviations:
      - inner shadows are painted after children;
      - node opacity is ignored rather than gating the blur;
      - there is no fill gate;
      - shadow `blendMode` is ignored;
      - there is no inner shadow on paths or text.
12. **The headless `pen` CLI is not 1.2.14.**
    - `pen interactive --in/--out` (CLI 0.3.5) embeds the 2.17 engine. It saved `version: "2.17"`, and its bundled `pen-schema.md` says 2.17.
    - It cannot produce 2.19 files or 1.2.14 renders; 0.3.9 is available and might.
    - The 1.2.14 evidence here came from driving Pen.app itself (`pen interactive -a desktop`, after `open -a Pen <file>`). That happened before the
      instruction to stay headless reached me, and I stopped driving the app when it did.
    - **Two probe documents are still open in Pen.app:**
      - `local/MKxE6U-pen-1.2.14/app1214/probe-opened.pen`
      - `local/MKxE6U-pen-1.2.14/app1214/probe-new.pen`

## B. Forward: what Woodcase does with a 1.2.14 file

Run on `local/MKxE6U-pen-1.2.14/fwd/unknowns.pen`. It is 2.19 and contains:

- a `fonts` root;
- an unknown key on a frame and one on a rectangle;
- a 200×90 `browser` in a vertical column.

`effect.pen` adds an unknown effect type, and `v3.pen` declares 3.0.

| Verb | Result |
|---|---|
| `woodcase tree` | Exit 0 with no warning. `browser  Web  0,50 0×0`. The column measures 300×100; Pen would make it 300×310. |
| `woodcase lint` | `warning pipeline document [migration] Format version 2.19 is newer than the supported 2.17…`, then **exit 1** |
| `woodcase get <browser>` | Exit 0, with the node's JSON intact |
| `woodcase set <rect> common.name=Top2` | Exit 0. A semantic diff shows: `version 2.19→2.17`; `fonts` dropped; `futureFrameKey` and `futureRectKey` dropped; `browser` kept |
| `woodcase render` (sandbox off) | Draws nothing for `browser` (`PenRenderer.swift:245-249` skips `.unknown`), and the layout is wrong as in `tree` |
| any verb on an unknown effect type | `not a .pen document — children[0].effect[1].type: Cannot initialize EffectType from invalid String value noise`, **exit 4** |
| any verb on `"version":"3.0"` | exit 4, `this build reads 2.17 and earlier 2.x`. That message is itself wrong: the build reads *newer* 2.x (`PenParserError.swift:93`) |

How the model decodes things it does not know:

- **Unknown node type.** It is preserved as `.unknown(typeName:properties:)`. Every key except the reserved common ones goes into
  `[String: AnyCodable]` (`PenNode.swift:96-99, 139-147`) and is re-encoded by `PenNode.swift:211-217`.
  - The layout engine treats the node as a leaf that fits its content, so it measures 0×0.
  - The renderer and the React emitter skip it.
  - `NodePropertyCodec` exposes its raw keys (`NodePropertyCodec.swift:117`).
- **Unknown key on a known type.** It is silently ignored by the synthesized `Decodable` of `PenNodeCommon` and the `*Data` structs, so it is gone
  from the model and never written back.
- **Unknown enum case.**
  - An effect `type` or a fill `type` throws `DecodingError`, and the whole document fails.
  - Other closed enums throw the same way, for example `shadowType`, `blendMode` and `layout`.
- **Unknown top-level key.** `PenDocument` models `version`, `themes`, `imports`, `variables`, `fileToken` and `children`. Everything else, including
  `fonts`, is dropped.

## D. Inner shadow

**What exists.** The pieces are the model (`shadowType`, `PenEffect.swift:76-86`), the CoreGraphics renderer and the React emitter.

- The renderer (`renderInnerShadow`) clips to the shape, then fills an even-odd donut of a margin rectangle minus the shape with a CoreGraphics shadow.
  CoreGraphics blur is 2σ, so σ = blur/2, which matches Pen.
- The React emitter writes `inset` in `box-shadow`, with blur passed through unchanged. That matches Pen's own CSS export, which writes the same
  `inset x y blur*2` form.
- `woodcase help schema` lists `shadowType: inner | outer`.

**What is missing or wrong:**

1. **2.19 vocabulary.**
   - `spread` is still modelled, still offered by the schema help (`PenEffect+Schema.swift:40`), still written by `set`, and still emitted to CSS
     (`ReactEmitter+Styles.swift:374-378`).
   - `renderSpread` draws it (`PenEffectRenderer.swift:58-113`). Our probe's `spread: 10` became a heavy black ring. No Pen version ever drew spread.
2. **Paint order.** Pen paints fills, then inner shadows, then the stroke, then children. Woodcase paints the inner shadow last:
   - in `postContent` for the non-blur path (`PenRenderer.swift:385-390`, `211-219`);
   - after children in `renderNodeContent` (`:550-558`).
3. **`blendMode`** on a shadow is ignored, for both outer and inner.
4. **Multiple outer shadows.** Only the first is drawn (`PenRenderer.swift:470-472`). This matters here because Pen writes `[outer, inner]` arrays.
5. **Legacy meaning.** Woodcase draws a pre-2.19 `"inner"` as inner. Pen has always shown it as outer, and 1.2.14 rewrites it. See open question 1.
6. **Fixtures.** The one 1.2.7 reference with an inner shadow, `render-transforms-and-effects.png`, shows it as outer, so it cannot check inner-shadow
   fidelity. A 1.2.14 export (`app1214/re/root2.png`) is the reference to use.

**Drawing it faithfully in CoreGraphics.** The existing inverted-path technique is right, and σ already matches (finding 8). What remains is to follow
Pen's recipe step for step:

- Build the shape path.
- Paint the inner shadows *before* `PenStrokeRenderer`, and before pushing children.
- For each inner shadow:
  1. `saveGState`, clip to the path, `setShadow(offset, blur·scale, color)` with the shadow's `blendMode`;
  2. fill the even-odd donut;
  3. `restoreGState`.

The one decision the geometry cannot make is how an inner shadow drawn under the children interacts with a frame that clips. Pen draws it before
`clipPath`, inside the node's shape, so the result is the same either way.

## E. Background blur

**Pen 1.2.14.** From its exported behaviour, the steps are:

1. `concat(localMatrix)`.
2. If opacity < 1, `saveLayer(alpha)`. The blur that follows then reads this empty layer: that is the opacity gate.
3. For each enabled `background_blur`: σ = `radius/2`, then `save`, `clipPath(maskPath)`, then `saveLayer(paint: Src, bounds: visualLocalBounds,
   backdrop: MakeBlur(σ, σ, Clamp))`, then restore both.
4. Then the fills, strokes and children.

Other properties:

- The blurred backdrop replaces the pixels inside the shape.
- The backdrop is whatever is already painted below the node, in any ancestor. Content just outside the node's bounds bleeds in: a teal band above the
  box tints the box's top edge in the export.
- Blurring happens in encoded sRGB.
- It scales with export scale: the @2x export gives the same sigma in points.
- Observed only, not traced: no blur when the fill is absent or fully transparent.

**RapidPro** (`../RapidPro`, read-only; summary from its sources):

- **Inputs.** It reads `PenBackgroundBlurEffect.radius` and `.enabled` through Woodcase's model (`PenEffect+RenderEffect.swift:38-41`).
- **Ordering and clipping.** The command is emitted after outer shadows and before fills (`RapidProRenderer+InstanceBuilding.swift:768-783`). It then:
  - ends the encoder;
  - blits the region of the main framebuffer under the node, padded by `ceil(2·radius)` = 4σ and rounded to 64 px
    (`BackgroundBlurData+BlurRegion.swift:13-56`);
  - runs `MPSImageGaussianBlur` with σ = radius/2 and clamp edges (`RapidProRenderer+Blur.swift:33-54`);
  - composites through a stencil of the node's SDF shape, which intersects ancestor clips (`RapidProRenderer+Encoding.swift:291-373`).
- **Gaps:**
  - node opacity does not gate or scale the blur;
  - there is no fill gate;
  - only the first blur is used;
  - the radius does not scale with the viewport zoom;
  - `.blur` together with `.backgroundBlur` on one node is unsupported.
- **Tests.** Its tests compare against Pen PNGs. It was written when Woodcase had no background blur (its `project/2026-04-08-implementation-plan.md:69`),
  and Woodcase's was later ported from it.

**Woodcase today** (`renderBackgroundBlur`, `PenEffectRenderer.swift:315-370`). On bitmap contexts it:

1. calls `context.makeImage()` on the **whole canvas**;
2. runs `CIGaussianBlur` (radius·scale, clamp) over the whole canvas on a software `CIContext`;
3. clips to the node's path, undoes the CTM and draws.

On PDF it does nothing. It runs after the opacity transparency layer begins (`PenRenderer.swift:327-344`), so the backdrop is multiplied by node
opacity instead of being suppressed.

**What a faithful CoreGraphics implementation needs.** These are listed by fidelity impact:

1. **Fix the flip.** Draw the blurred `CGImage` at `(0, 0, w, h)` in the un-CTM'd space. Add a regression test with a *vertically asymmetric*
   backdrop; `blur1` is symmetric, which is how the flip went unnoticed.
2. **Match the sigma.** `CIGaussianBlur` `inputRadius = radius × scale / 2`. Apply the same halving to `renderBlur`: it should be `radius × scale / 2`
   pixels, not `radius`.
3. **Blur encoded sRGB.** Create the `CIContext` with `.workingColorSpace: CGColorSpace(name: CGColorSpace.sRGB)` (non-linear) or `NSNull()`, and
   with an output colour space equal to the bitmap's.
4. **Pen's gates.** A fill with no visible alpha means no blur; opacity < 1 means no blur. These are faithful to Pen but arguably Pen bugs: open question 2.
5. **Region, not canvas.** Crop the capture to the node's device bounds plus 3σ, which is what Pen's `inflate(a*3)` trigger bounds use. The current
   cost is O(canvas pixels) per blurred node: a full `makeImage` copy plus a full-extent Core Image blur. That is quadratic in practice on screens
   with many glass cards.
6. **Clip and corners.** Clipping is correct today: `PenShapeBuilder.buildPath` covers corner radii, ellipses and paths. Keep ancestor clips; they
   survive because `clip()` intersects.
7. **Say when it did not happen.** Emit a diagnostic when `CIFilter` or `createCGImage` returns nil (finding 9), and on non-bitmap contexts.
8. **Test with an edge profile, not an MAE.** `blur1` passes at MAE 1.41 while mirrored and twice too wide. Assert a fitted sigma, or pixel values
   across a known edge, against a 1.2.14 export.

**What must stay in step with RapidPro.** It shares the model, so these are shared semantics:

- sigma = radius/2 (RapidPro is right);
- the opacity gate and the fill gate (both repos are wrong, if we mirror Pen);
- inner-shadow paint order (both wrong);
- `spread` (both implement it; Pen never did).

The sigma convention and the gates should be written once, in Woodcase: for example `PenEffect.sigma(forRadius:)`, and a
`PenBackgroundBlurEffect.isEffective(on:)` that RapidPro calls. Neither repo should hand-code a constant.

## F. Lenient versioning, proposed rule

**Rule:**

1. **No `version`:** legacy, as today.
2. **Same major, minor < 2.11:** migrate, as today.
3. **Same major, minor ≤ modelled:** decode.
4. **Same major, minor > modelled:** decode leniently, with unknowns preserved (G). Emit **one `notice`-severity diagnostic** saying the version is
   newer than this build's. A notice does not make `lint` exit 1: lint's exit should mean "the design has a problem", and a newer Pen is not one.
   **Write the declared version back unchanged.** Never downgrade.
5. **Different major:** run a *structural probe* before refusing. The probe passes when all of these hold:
   - the root is an object with a `children` array;
   - every node is an object with string `id` and `type`;
   - at least one node has a type we model;
   - every node of a modelled type decodes under the lenient decoder without a **type conflict** on a key we model. A type conflict means a known key
     holding a value of an incompatible shape, such as `width: {…}`, or `effect.type` present but `fills` restructured.

   If the probe passes, read verbs work, with a `warning` naming the major. **Writes are refused** (exit 5) unless Ben rules otherwise (open question 3).
   If it fails, refuse as today, with a message naming the first conflicting path.

**Detecting "a truly different schema"** is exactly the type-conflict count above. An unknown key, node type or enum case is *drift*, and G preserves
it. A known key whose value no longer fits its modelled shape is *a different schema*. The decoder can report this precisely, because each conflict
is a `DecodingError.typeMismatch` or `.dataCorrupted` at a modelled key's coding path.

**What the CLI says:**

- a newer minor: `note: format 2.19 is newer than this build's 2.17 — 3 unknown keys and 1 unknown node type are carried through unchanged; the file is written back as 2.19`;
- a different major that passes the probe: `warning: format 3.0 is a different major version; reading it with the 2.x model, writes refused`;
- a failing probe: `format 3.0 is not one Woodcase can read: /children/0/width is an object, which 2.x models as a number or sizing keyword` (exit 4).

Also fix `PenParserError.swift:93`: "this build reads 2.17 and earlier 2.x" is false.

**Interaction with a model bump.** Writing back a newer declared version is only safe if Woodcase never *introduces* a key that the newer version
removed. If Woodcase still wrote `spread` into a file declaring 2.19, Pen would reject the file: `Insert` of such an effect was refused. So the model
must track Pen: bump to 2.19 (leaf 3) before or together with the write-back rule. From then on, each time a newer minor appears the same question
comes back, and the lint notice is how we learn of it.

## G. Round-tripping unknown keys, options and a recommendation

What exists already:

- `AnyCodable` (`Models/AnyCodable.swift`), whose doc comment already claims it is used "to preserve unknown fields".
- `DynamicCodingKey`.
- `.unknown` node kinds, round-tripped.
- `PenMetadata`, verbatim.
- `NodePropertyCodec`, which treats `.unknown` nodes as raw bags.
- `PenNodePatcher`, which merges an override onto a node's JSON: "a key survives exactly when the node's type decodes it".

The editing layer stores typed `PenNode`s in a flat store (`EditableDocument.nodes`), and writes go through `PenFileTransaction.encode(_:for:)` and
the CRDT replicas.

**Options:**

1. **Typed nodes plus opaque `extras` everywhere the format can drift.** This is the recommended option.
   - A single `PenExtras` struct (`Friendly`, wrapping `[String: AnyCodable]`) holds keys the decoder did not claim. It is captured by a
     `DynamicCodingKey` pass minus the kind's known key set, a set that `PenSchemaTable` already has.
   - It is added to `PenNode` for node-level keys and to `PenDocument` for the root.
   - It is also added to the payload structs that Pen extends: shadow, blur, background-blur, fill variants and stroke.
   - Discriminated unions gain an explicit `.unknown(typeName:payload:)` case: `PenEffect`, `PenFill`, and any future one. The renderer and the React
     emitter already switch exhaustively, so the compiler finds every site, and RapidPro's too.
   - Unknown node types keep `.unknown`, but the layout engine reads `width`/`height` from its properties (a number or a sizing keyword) and places it
     as an inert box. The renderer draws nothing, and the viewer could hatch it.
   - Extras are never read by layout, rendering or codegen. They are write-through only.
2. **Keep the raw JSON object beside each typed node, and merge on encode.** This preserves everything without touching the model. But it means two
   sources of truth, and a stale raw value can resurrect a key a verb removed. It also breaks "one shared struct across a serialization seam", and
   Swift dictionaries do not preserve key order anyway, so it buys no byte-stability. Rejected.
3. **Decode known structure and keep the whole document as `AnyCodable`, applying edits as JSON patches.** Maximal fidelity, but it throws away the
   typed model the editor, CRDT, layout and codegen are built on. Rejected: it is a rewrite, not a feature.
4. **Strict refusal.** Fail on any unknown key instead of dropping it. This is honest, but it makes every new Pen feature a hard failure, the opposite
   of brief item 4. Useful only as a `--strict` mode on `lint`.

**Weighed against the house principles.**

- *Strongly typed*: option 1 keeps every modelled key typed and confines `AnyCodable` to the part we genuinely cannot type, opaque and unread.
- *One struct across the seam*: `PenExtras` is the single definition that Woodcase, the CRDT snapshot and RapidPro all see.
- *BUILD stage, no compatibility shims*: this preserves the *upstream* format's future keys. It is not a shim for old Woodcase files, so it does not
  conflict with the rule.

**Editing verbs:**

- **`set` on a modelled key.** Unchanged. By construction, extras never hold a modelled key, so no extra can shadow a property. When a later Woodcase
  models a key, it simply stops being an extra.
- **`set` on an unmodelled key.** It stays refused (`unknownProperty`), with a hint that the key is preserved and names which keys are. Whether an
  `extras.<key>` path should allow writing is open question 4.
- **`add`, `replace`, `set -F`.** Authoring input must stay **strict**. Extras are captured only when *decoding a file*, never from an agent's JSON;
  otherwise a typo like `"fil"` would be silently kept instead of refused. This needs two decode modes, file and authoring, selected by a
  `CodingUserInfoKey`.
- **`cp`.** Copies extras with the node.
- **`rm`.** Removes them.
- **`replace`.** Replaces them with the replacement's (none, from authoring).
- **Overrides.** `descendants` bags are merged by `PenNodePatcher` as JSON. Unknown keys in a Pen-written override then survive, because the target
  node now has extras to land in. Test this: an override that sets an unknown key on an instance child should round-trip.
- **CRDT.** Extras must be part of the replica state, or a merge drops them. The simplest correct choice is one last-writer-wins register per node
  holding the whole `PenExtras`. Only file decodes ever write it, so it never contends.
- **Revisions.** Revisions hash canonical encodings (`EditableDocument+Revision.swift:223`), so extras are covered automatically.

**Key order and byte-stability.** Woodcase writes `.sortedKeys` (`PenParser.swift:189-191`), and extras merge into that order. A Woodcase write of a
Pen-saved file therefore reorders keys throughout, which is already true today (the 2.17 migration doc noted Pen's `type, id, x, y, name, …` order).
Byte-stability holds between Woodcase writes, not across tools. Semantic equality is the round-trip test.

**Recommendation.** Option 1, plus these companions:

- typed `fonts` on `PenDocument`, since it is a real Pen feature;
- a typed `browser` node, since it is in the 2.19 schema and affects layout;
- sized `.unknown` nodes;
- a lint `notice` listing preserved unknowns, so drift is visible.
