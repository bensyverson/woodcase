# Pen CLI 0.3.13 (format still 2.21): sampler uniforms, a shadow change, and no comments in the format (2026-10-23)

Author: Claude (Opus 5.5), leaf `9UroXC`, for Ben. Findings and a recommendation; the tasks block at the end is a proposal, not imported.

**In short.** The format is still 2.21. The only format-level change is new values for a shader's `sampler2D` uniforms: an image URL, `"pencil:object"` or `"pencil:background"`. Woodcase already round-trips them losslessly, but it types them as colors. **One rendering change is revisionary:** an outer shadow is now cast from the node's rendered content, not a frame's box — so a frame with no fill casts its children's shadows, and a line casts one too (corrected 2026-10-28, see below). Woodcase's references and renderer follow it since leaf `LB02SZ`. **Pen's CLI knows nothing of comments.** Its documented schema has none. Its engine rejects a `comments` key at the root or on a node and drops it on save. If Pen.app 1.2.x has comments, the CLI can't show where they live. We can't look inside the app under Ben's 2026-10-14 rule, so this survey can't answer that. The *Comments* section says how Ben can settle it in five minutes.

> **Update (2026-10-23, same leaf):** Ben ran that test, and Pen.app does have comments. **They are not stored in the `.pen` file.** The file he saved with comments holds no comment data at all; see *Pen.app's comments file*. The recommendation, keep ours, stands.

## What changed in the docs (0.3.11 → 0.3.12 → 0.3.13)

Method: `npm pack @pen.dev/cli@0.3.11 @pen.dev/cli@0.3.12 @pen.dev/cli@0.3.13`, then extracting only `*.md` (`tar -xzf … --include='*.md'`) and `diff -r` between versions.

- **0.3.11 → 0.3.12: no Markdown changed.** All 15 `.md` files are byte-identical. 0.3.12's changes are code only, so they're invisible to this method.
- **0.3.12 → 0.3.13:** two files changed, `pen-schema.md` and `scripts-and-shaders.md`, and both changes are about shader samplers:
  1. **`ShaderUniforms` gains a sampler2D shape.** The allowed values now include "image URL or `pencil:object`/`pencil:background` string (sampler2D)". The doc comment on the shader effect now says a `sampler2D` uniform *set to* `pencil:object` is bound to the rendered node; it used to say a uniform *annotated* `@content`.
  2. **`@content` and `@backdrop` leave the docs.** They no longer appear in the list of uniform annotations. Their meanings move, word for word, to the two special URLs: `"pencil:object"` is the node's own rendering below the shader, and `"pencil:background"` is what's behind the node, mirrored outside it. The pixelate example now uses `/** @label Content */` with `"uniforms": { "u_content": "pencil:object" }`.
  3. **Image samplers are documented.** A sampler2D can take an image URL, "loaded as with UNPACK_FLIP_Y_WEBGL, so `texture2D(tex, gl_FragCoord.xy / resolution)` shows the image upright".
- **The CLI's tool surface.** `pen interactive --help` 0.3.11 against 0.3.13 (0.3.11 installed with `npm install --prefix local/9UroXC-pen-0.3.13/cli-0.3.11 @pen.dev/cli@0.3.11`) differs only in a new optional `description` parameter on `execute`: "Shown to the user as the label of this call". `pen --help` is identical. The `browser` tool and its `browser` node type were already in 0.3.11.
- No other node, property, effect or enum changed, and the version line is unchanged.

## Behavior: 0.3.13 against 0.3.11

Probes (`local/9UroXC-pen-0.3.13/probes/`), run through `scripts/pen-oracle <file> --scale 1 --accept-invalid` under each CLI (0.3.11 first on `PATH`). Pixels were read with `peep sample <png> 50 50`:

| Probe (`shader-object.pen`, red 100×100 frames, shader swaps to `.bgra`) | 0.3.11 | 0.3.13 |
|---|---|---|
| effect, sampler annotated `/** @content */`, no `uniforms` | `#0000ff` (runs) | `#0000ff` (runs) |
| effect, `@label Content`, `uniforms: { u_content: "pencil:object" }` | `#00000000` (sampler unbound) | `#0000ff` (runs) |
| effect, `@label Content`, no uniform value | `#00000000` | `#00000000` |
| control, no effect | `#ff0000` | `#ff0000` |

`shader-background.pen` gives the same result for fills: a `/** @backdrop */` sampler works in both versions, and `"pencil:background"` works only in 0.3.13.

- **The old annotations still work in 0.3.13.** Files written for 2.21 as first documented keep rendering. The new spelling is additive.
- **No migration on save.** The 0.3.13 re-save of both probes is identical to 0.3.11's apart from `fileToken`, so `@content` shaders aren't rewritten to `pencil:object`. The format version doesn't move either, so a file can't say which spelling it needs. A `pencil:object` file opened in 0.3.11 (Pen 1.2.16) draws a transparent node.
- **Fixture sweep: two real rendering changes.** The sweep covered all 42 fixtures that have a committed Pen re-save (`Tests/WoodcaseTests/Fixtures/*.pen-saved.pen`). Each ran through `scripts/pen-oracle <fixture> --scale 1 --accept-invalid` under 0.3.11 and under 0.3.13, and the two outputs were compared directly: PNGs with `cmp`, then `peep compare`; layout JSON byte for byte; re-saves with `fileToken` dropped. The runner and comparer are scratch scripts, not kept.
  - Results: **294 of 333 PNGs are byte-identical, and all 41 layouts are identical.** 41 of 42 re-saves are identical. The odd one out is `slot-override-keys`, whose id Pen mints for an injected descendant is random on every run (known since the 2.21 survey).
  - **Outer shadow on a frame with no fill now follows its content.** `render-shadows-outer-frame-children` (MAE 8.1) is a fill-less, unclipped `holder` frame with an outer shadow and two filled children. 0.3.11 cast one shadow from the frame's whole 140×140 box. 0.3.13 casts it from the children: a shadow under the square and one under the circle, as Figma does. The same change shows in `render-group-shadows-group-frame-child` (MAE 2.5), and smaller in `-group-stroke-path` (0.6) and `render-sizeless-frames-paint` (0.9).

## What Woodcase, RapidPro and Penumbra do today

Probed with the repo's debug build, `.build/debug/woodcase` (`woodcase --version` prints `0.1.4 (.pen 2.20)`, the same as Homebrew's).

- **Read:** both probe files read, with the known notice `Format version 2.21 is newer than this build's 2.20 … written back as 2.21` (`woodcase tree local/9UroXC-pen-0.3.13/out-0.3.13/shader-object.pen-saved.pen`). Leaf `45iUT4` is still open.
- **Round-trip:** `woodcase set shader-fill-samplers.pen glass kind.width=110` on a shader fill whose uniforms are `"pencil:object"`, `"pencil:background"`, `"./tex.png"`, `"#00FF00"` and `0.5` writes every value back unchanged. Only the key order changes.
- **Typing is wrong, but harmlessly:** `PenShaderUniform.init(from:)` (`Sources/Woodcase/Models/PenFill+ShaderFill.swift`) decodes any string that doesn't start with `$` as `.color`. So `"pencil:object"`, `"pencil:background"` and `"./tex.png"` all become `.color(…)`. They survive because `.color` re-encodes its string verbatim, and nothing parses a uniform's color: lint, the variable resolver and import prefixing only touch `.variable`. The bug would surface once something reads `.color` as a color: the inspector (Penumbra's uniform editing), a typed authoring path, or schema help. Shader effects still decode as `PenEffect.unknown` (leaf `ugIGZF` is open), so their uniforms aren't typed at all yet.
- **Render:** `woodcase render … --scale 1` draws every probe frame red: shaders aren't run, which is the known fallback. `woodcase lint shader-fill-samplers.pen` warns `shader-not-drawn` for the fill. The shader *effect* is still silent: `woodcase lint` prints nothing for `shader-object.pen-saved.pen`, as the 2.21 survey found.
- **RapidPro and Penumbra** see uniforms only through Woodcase's types, and neither switches over `PenShaderUniform` (`grep -rn PenShaderUniform` in both repos finds nothing). Nothing breaks.

**Nothing is broken today, but the references are now one Pen behind.** Woodcase needs:
- a type fix, folded into the open shader-effect leaf;
- a decision on the fill-less frame's shadow, as Pen 1.2.16 drew it or as 0.3.13 does.

It doesn't need a new format version, a migration or a new node type. Woodcase renders the shadow-children case as the committed reference does, which is Pen's old box shadow; the suite passes against it.

> **Update (2026-10-23):** this was the CLI's evidence. Pen.app's own saved file confirms it rather than correcting it. Pen.app has comments, but they aren't in the file; see *Pen.app's comments file* below. "If Pen.app now has comments" is now "it does".

- `probes/comment-keys.pen` puts a `comments` array at the root and on a frame, plus `metadata.comments`. On load, 0.3.13 reports `/comments - unexpected property` and `/children/0/comments - unexpected property`. **The re-save drops both arrays and keeps `metadata` intact** (`out-0.3.13/comment-keys.saved.pen`).
- `get_app_state()` lists the canvas, selection, components, the integrated browser and the account, and nothing about comments.

**What that means.** If Pen.app now has comments, the CLI build that shipped the same day doesn't put them in the `.pen` format. They are either:

- kept outside the file (the CLI has pen.dev cloud workspaces, `pen --list-workspaces`, which would be a natural home), or
- in an app-only schema the CLI hasn't caught up with.

Either way, a `.pen` file that passes through the headless engine loses any `comments` key, and keeps a comment only if it lives in `metadata`, as ours do.

**How Ben can settle it (about five minutes, no reverse engineering).** Pen writes the file; we only read our own data.
1. In Pen.app, open a small file of Ben's, comment on a node, reply once, resolve the thread, and save.
2. Send the `.pen` file. `git diff --no-index` against the file from before the comment shows exactly what Pen writes.
   - If nothing changed but `fileToken`, Pen's comments live in its cloud and the format has no say.
   - If something changed, the diff gives the keys, the anchoring, the authorship and the resolved state, which is the evidence the brief asked for.
3. Optionally, with that file open in Pen.app: `pen interactive -a desktop` with `read_skill({ path: "pen-schema.md" })` and `get_app_state()`, if Ben counts the app's schema as served through the CLI as allowed.

**Our convention** (Penumbra `project/2026-10-11-notes-comments-and-spans.md`, decision 8 and its rulings):
- Each message is a root-level `note` with `metadata.woodcase.type: comment`.
- The first message carries `anchor {node, x, y}` and `state` (open or resolved). Replies carry `replyTo`, and every message has `author` and `createdAt`.
- Woodcase's `comment`, `reply` and `resolve` verbs stamp these.

**Recommendation: keep ours, and map to Pen's on import and export only if Pen's turns out to be in the file.** The reasons, against what Pen's CLI does today:

- **Pen round-trip.** Ours survives Pen today: probed on 2026-10-11 and again here, Pen keeps a note's `metadata` whole. A Pen-native `comments` key would be *deleted* by every Pen engine before the one that adds it, including the CLI we test against. Adopting a representation Pen's own CLI strips would lose comments the first time a file passes through `pen`.
- **Multiplayer merge.** One note per message means two people replying at once append two independent nodes, with no conflict. Each message has its own id and its own `createdAt`, and resolving touches one key on one node. Any representation that nests replies in an array on the anchor node or a thread object makes concurrent replies a conflict on one array, which pencilcase's op relay and the shared-history log would have to merge element-wise. Ours already merges per node and, within `metadata.woodcase`, per key.
- **Agents.** `woodcase comment`, `reply` and `resolve` write whole nodes, which `woodcase tree`, `set` and the relay already understand. A separate comment store would need its own read path, verbs and diffs.
- **The cost of ours.** In Pen, our comments show as ordinary notes: a pile of root-level sticky notes, with no bubble or thread. That's visible and readable, not lost. A Pen user who resolves or replies in Pen can't do it through our keys.

**If the diff in step 2 shows Pen stores comments in the file**, the choice becomes: map on import/export (a `woodcase migrate`-style rule both ways, ours staying canonical), or adopt. Adopting would make sense only if Pen's shape also merges per message, and only once every Pen we support keeps it. Until that evidence exists there is nothing to change.

## Item 6: areas Ben is discussing (malleable Penumbra)

- **Shader fills and shader effects: changed.** A shader's texture inputs are now data in the file rather than annotations in the GLSL. Any `sampler2D` uniform can be bound to an image URL, to the node itself (`pencil:object`) or to the backdrop (`pencil:background`), per node, in `uniforms`. That makes a shader file a reusable effect with declared, per-use inputs, closer to a parameterized component. `@mouse` and `@time` (interactive and animated shaders) are unchanged and were already there in 0.3.11. Running shaders stays parked (Woodcase backlog, *2026-09-27 — Running shader fills and script nodes*).
- **Script nodes: unchanged.** Still `scriptUri` plus `inputs`, with `@input name: type [= default]` declarations (number, string, boolean, color, ref, enum) and `@schema 2.11`.
- **Browser nodes: unchanged** in the schema (`url`, `deviceId`, `zoom`, scroll, corner radius, effects, stroke). The `browser` MCP tool (load, import-to-canvas, screenshot, return DOM, raw CDP in six domains, driving a browser node by `nodeId`) was already in 0.3.11.
- **Declared inputs or parameters on components or artboards: nothing new.** The only declared inputs are still script `@input`s and shader uniforms.
- **Data binding: nothing new** beyond variables and themes.
- **Interactivity or prototyping: nothing new.** No links, triggers or flows in the schema. The only interactive input is the shader `@mouse` uniform.
- **Animation or time: nothing new.** The only time input is the shader `@time` uniform.
- **Plugins or extensibility: nothing new** in the format. On the tool side, 0.3.13 adds only `execute`'s `description` label. The `pen` agent flags (`--agent`, `--model`, Codex login) aren't in the format.

## Proposed plan

1. **Woodcase: fold the sampler uniforms into the open shader leaf `ugIGZF`** rather than opening a parallel one. Its shared `PenShaderUniforms` type should add a sampler case, with Pen's three sampler shapes: an image URL, `pencil:object` and `pencil:background`.
   - Decode a string as a color only when it is a hex color (`#RRGGBB[AA]`). Decode `pencil:object` and `pencil:background` as the two special cases, and any other string as an image URL, kept verbatim and file-relative like the shader's `url`.
   - Schema help documents the three values. `@content` and `@backdrop` remain valid in shader source (0.3.13 still honors them), so lint shouldn't flag them.
   - The leaf's desc gets this paragraph (an edit to `ugIGZF`; this survey didn't make it, per the brief). If Ben prefers a separate leaf, the block below files one, blocked by `ugIGZF`.
2. **Woodcase: follow 0.3.13's outer shadow on a fill-less frame.** The shadow comes from the frame's rendered content (its children), not its box. Regenerate the affected references with `scripts/pen-oracle` under 0.3.13: `render-shadows`, `render-group-shadows` and `render-sizeless-frames`, plus `render-shader-fills` for the flipped image, which needs no renderer change. Then make the CG renderer match, and RapidPro if its shadow path differs.
