# Pen 1.2.15 (format 2.20): version handling, image fills, release 0.1.3 (2026-10-03)

Author: Claude (Opus 5.5), for Ben. Plan and findings; the tasks block at the end is imported into `job`.

## How this started

Ben's c41x spec sheets (`../c41x/design/specs/*.pen`) exported blank PDF pages. The cause was the release, not the code:
Homebrew's `woodcase` 0.1.2 was tagged at `8cebb0a`, one commit before the PDF fix `d23c0ff`. Measured with
`woodcase render c41x-technical-report.pen --format pdf` (5 pages, 612×792): with 0.1.2, `CGPDFDocument` reads every page's
`mediaBox` as `(0,0,0,0)`, and `pdftoppm -r 50` draws pages 2–5 blank. A release build of `main` reads `(0,0,612,792)` on every
page, and all five draw. This is issue `OMNE7c`. One leftover remains: the page tree still carries the context's initial
`/MediaBox [0 0 0 0]` (`LC_ALL=C grep -a -o '/MediaBox *\[[^]]*\]' x.pdf`). Readers use the per-page box, but the default
should be a real one.

The same session found that Pen.app 1.2.15 (with `pen` CLI 0.3.10) writes format **2.20**.

## Findings

1. **Pen 1.2.15 saves `"version": "2.20"`, and its validator accepts only that value.** Its bundled schema
   (`/Applications/Pen.app/Contents/Resources/app.asar.unpacked/out/skills/pen-dev/pen-schema.md`) differs from 2.19 in image fills only:
   - `mode` is `"cover" | "contain" | "stretch"`, and a missing mode means `cover`.
   - There is a new optional `transform`: an affine `[a, b, c, d, tx, ty]` that crops the image (described below).
2. **Pen upgrades a 2.19 file's image paints like this:** `fill` → `cover`, `fit` → `contain`, `stretch` stays, and a *missing* mode
   becomes an explicit `stretch`. A missing mode therefore meant stretch in 2.19 and means cover in 2.20; the upgrade keeps old files
   looking the same. Observed with `pen interactive --in probe219.pen --out probe220.pen` (`save()`), four rectangles with
   modes fill/fit/stretch/absent. It applies to image paints in a node's `fill` and `stroke`, and inside ref `descendants`.
   **Unverified:** whether Pen's upgrade reaches an image paint nested in a stroke's own `fill` key. Probe it before relying on it.
3. **Shadow `spread` stays dropped**, as it has been since 2.19. Ben, 2026-10-03: no warning and no reintroduction.
4. **Pen's re-save also drops keys whose value is the default:**
   - `layout: horizontal` on frames;
   - `fit_content` sizes;
   - `fontWeight: "400"`;
   - `x`/`y` 0, `gap` 0;
   - `strokeLinecap: butt`;
   - `alignItems: start`.
   
   It also rewrites path geometry to compact relative form. For all four c41x files, Woodcase's renders of Pen's 2.20 re-save are
   pixel-identical to its renders of the 2.19 originals (`peep compare`: 0.0 on all eight pages, `woodcase render --format png`). Woodcase's
   defaults agree with Pen's for every key Pen dropped.
5. **Woodcase today refuses any 2.20 file with an image fill.** The error is "Cannot initialize PenImageFillMode from invalid String value
   cover", because `PenImageFillMode` is a closed synthesized enum (`Models/PenEnums.swift:97-101`). Woodcase also treats a missing mode
   two ways:
   - the CG renderer and the SwiftUI emitter treat it as stretch;
   - React treats it as cover (`ReactEmitter+Styles.swift:195`, `+Frame.swift:105`, `+PaintLayer.swift:83`, `+SVGStrokePaint.swift:221`).
6. **Our version-gated migration would misfire at 2.20.** `PenLegacyMigrator.rules(upgrading:)` returns every modern rule for any
   version below `current`. Bumping `current` to 2.20 would run the 2.19 shadow rule (inner → outer, drop `spread`) on genuine 2.19
   files, and destroy their inner shadows. Each rule must say which version it upgrades *from*. The parser's `mayApply` shortcut
   (`PenParser.swift:92`) also assumes the shadow rule is the only modern rule.

## Image crop: the behavior to match

Ben's ruling: implement our own version that matches Pen's behavior; do not port Pen's code. The behavior below is stated in
our terms. Confirm every clause with `scripts/pen-oracle` probes before treating it as settled, and correct this section in place if a
probe disagrees.

> **Confirmed 2026-10-03 (leaf `X6YNC3`):** every clause below matches Pen 1.2.15's exports of `render-image-crops.pen`
> (48 boards, `scripts/pen-oracle --scale 2`), read by a least-squares fit of the UV image's red and green against pixel
> position, and `PenImagePlacement` implements it (CG MAE 0.002–0.076 per board, `swift test --filter PenImageCropSnapshotTests`).
> Two clauses are sharper than written: the crop box's unscaled sides are *always* the lengths, in image pixels, of the
> crop square's x and y axes mapped back through T's inverse (for a scale-only T that is width ÷ |a| and height ÷ |d|; a
> quarter turn swaps them — "horizontal scale" alone does not say which); and cover's shrink is measured on the
> axis-aligned bounds of that mapped-back window, in the image's unit square, about the window's center, by the larger
> overflow — a 1.3-wide sheared window is shrunk by 1/1.3. The move that follows keeps those bounds inside the unit square.

Coordinates:
- **Image space** is the image's unit square: (0,0) at top-left, (1,1) at bottom-right.
- **Crop space** is the unit square of the crop box.
- `transform` `T = [a, b, c, d, tx, ty]` maps image space to crop space: `x' = a·x + c·y + tx`, `y' = b·x + d·y + ty`.
- So `[2, 0, 0, 1, -1, 0]` shows the right half of the image across the whole crop box.
- A missing transform is the identity, which is no crop.

Placement of the crop box in the node's bounds (`w × h`):
- **stretch:** the crop box is the node's bounds.
- **cover / contain:**
  - The crop box is first given the aspect ratio of the *cropped* image. Its unscaled width is the image's pixel width divided
    by T's horizontal scale; its height is the pixel height divided by T's vertical scale.
  - With a sheared or rotated T, use the lengths T's inverse gives the crop square's axes in image pixels.
  - The box is then scaled uniformly to cover (the larger scale) or fit (the smaller) the node's bounds, and centered, exactly as a whole
    image would be.
  - With no transform, this is ordinary centered cover/contain.
- **contain with a transform** clips drawing to the crop box, so image outside the crop never shows. stretch and cover do not clip to
  the crop box; the node's own shape clips as usual.
- **cover keeps the crop inside the image.** Before placement:
  - If the crop region, mapped back into image space, is larger than the image on either axis, it is shrunk uniformly until its larger
    side fits.
  - Its center is then moved, as little as possible, so that the region lies within the image.
  
  A cover crop therefore never shows past the image's edge.

The image is drawn into the crop box through T. Pen's DOM export does the same thing in CSS: a full-size background layer with a
`transform: matrix(...)`, wrapped in an `overflow: hidden` box for contain. This is a hint for the React emitter, not code to copy.
