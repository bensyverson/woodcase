# Code Generation

Generate production UI code from .pen design documents.

## Overview

Woodcase's code generation pipeline transforms parsed .pen documents into production-ready UI code without using an LLM. The pipeline diverges from the render pipeline after import resolution:

```
Parse → Import Resolve → Analyze → Emit
```

Unlike the render pipeline, code generation does **not** expand refs or resolve variables — refs become component instantiations, and variables become CSS custom property references (e.g., `var(--bg-card)`). The target platform handles layout at runtime.

### Analysis

Three analyzers extract structured metadata from a ``PenDocument``:

- ``ComponentAnalyzer`` finds all reusable nodes and extracts their props (from `_props` metadata), actions (from `_role` on the node or a descendant, named by `_action` where one is written and `click` by default on a `button` or a `link`), and bindings (from `_role` alone — a `textInput`, `toggle` or `select` node becomes a binding named after that node). Each prop includes a `targetNodeID` for matching against ref override keys. The analyzer also resolves interactive state information: it parses the component's ``ComponentRole`` from `_role` metadata **on the reusable node's own root**, discovers state variants from `{Name}:{state}` siblings and `_states` metadata, diffs them with ``NodeDiffer``, and fills gaps with smart defaults from ``RoleStateMapping``.

> Correction (2026-09-02): this page previously said bindings come from `_role` + `_bind`. There is no `_bind` key — no version of ``ComponentAnalyzer`` has ever read one, and writing it into a document does nothing. Bindings come from `_role` alone. ``ComponentDefinition/actions`` and ``ComponentDefinition/bindings`` are also collected but never emitted: no emitter reads either, so `_action` records intent and changes no output today.

The CLI teaches the same ground to agents, and is the primer to reach for first: `woodcase help codegen` names every metadata key that is read, the deep-key `set` command that writes one, and a worked example that ends in a typed props interface.
- ``PageAnalyzer`` finds top-level non-reusable frames, which represent pages/screens in the application.

A page and a component are named by one rule: a leading `Component/` folder (for a page, also `Screen/` or `Component/Screen/`) is dropped, a single word keeps its casing with its first letter capitalized (`FilledCard` and `filledCard` are both `FilledCard`), and several words are each capitalized and joined (`Tab Bar` is `TabBar`). A component whose name another component already has, ignoring case, is numbered from 2 in document order (`Card`, `card` → `Card`, `Card2`), so two components never share a file on a case-insensitive disk. A page named like a component is suffixed `Page` (`FilledCardPage`), so its file can import the component, and a page whose name another page already has, ignoring case, is numbered from 2 in the same way. A name the generated code already means something by is reserved (`CodeGenName.reservedNames`): ECMAScript's globals (`String`, `Map`, `Date`, `JSON`, …), the web platform constructors a module calls by name (`Image`, `Text`, `Node`, `Event`, `URL`, `Response`, …), React's capitalized exports (`React`, `Fragment`, `Component`, `Suspense`, …) and the package's own `ThemeProvider`. A component with a reserved name is suffixed `Component` (`TextComponent`) and a page `Page` (`StringPage`), then numbered like any clash — until issue `8xg1Mt` a frame named `string` became `function String`, shadowing the global in its module. An icon import follows the same rule inside each file: where its name is reserved, a component's, the file's own, or the same name already imported from another family, it is imported under an alias of its name and its family's (`Map as MapLucide`, `VpnLock as VpnLockRounded`, `Bell as BellLucide` beside a `Bell` component); before, two families' `VpnLock` were imported twice under one name, which does not compile. Every emitter, the manifest and the viewer take the names as ``ComponentAnalyzer`` and ``PageAnalyzer`` give them; SwiftUI then renames a type that would shadow one of its own.
- ``ThemeAnalyzer`` extracts theme axes, variables with their themed values, and nodes with theme context overrides.

```swift
let doc = try PenParser.parse(contentsOf: url)
let components = ComponentAnalyzer.analyze(doc)
let pages = PageAnalyzer.analyze(doc)
let theme = ThemeAnalyzer.analyze(doc)
```

### Prop Mapping

When a ref node overrides descendant properties, ``PropMapper`` bridges between ref override keys (node IDs) and component prop names. It reads override values from ``PenDescendantOverride`` and returns them typed, as ``PropMapper/Value`` — a string, a colour (a literal or a variable), a boolean or an image URL — so each emitter formats them in its own syntax: React writes `"Custom Title"`, `"var(--primary)"` or `{false}`.

The bridge is ``ComponentDefinition/propsByNodeID``, and it is **one-to-many**: several props may name one descendant, because a node has several fields to read — a `label` taking a text node's content and a `tint` taking its fill are two props of one node, and one override of that node feeds both. Two props of the same *type* on one node read the same field and are ambiguous; the mapper emits the first by prop name, and `lint` reports the pair under `codegen-prop-path` with the edit that separates them.

When a ref has descendant overrides that **cannot** be mapped to declared props (unmapped overrides), the emitter *inlines* the component — cloning the source node tree, applying overrides via ``PenNodePatcher``, and emitting the expanded nodes directly instead of a `<ComponentName>` tag. A diagnostic warning (or error in strict mode) is emitted when this occurs.

`woodcase lint` reports this before the emitter runs, as `codegen-unmapped-override`, along with a `_props` entry that resolves to no descendant (`codegen-prop-path`) and a `_role` outside ``ComponentRole`` (`codegen-role`) — the three declarations codegen reads and silently discards. The path resolution is shared, not duplicated: both the analyzer and the lint call ``ComponentAnalyzer/resolveDescendantPath(_:from:)``. See <doc:WoodcaseLint>.

### Shared decisions and target syntax

Everything under `CodeGen/` outside `React/` and `SwiftUI/` is target-neutral, so a second emitter reuses the decisions without inheriting any CSS or JSX: the analyzers, ``PropMapper``, `InstanceOverrides` (which of an instance's overrides its props carry, which change nothing, and which need a copy — SwiftUI reads it; React still inlines only for a key no prop names), ``ManifestEmitter``, ``EmitResult``, and the paint layer in `CodeGen/Paint/`. `CodeGen/React/` holds everything that is web: the emitter itself, ``StateEmitter``, ``ThemeEmitter``, ``PackageScaffolder``, ``ViewerScaffolder``, ``FontsourceMapping`` and ``IconLibraryMapping``. A decision moves into the shared layer when a second emitter needs the same one, not before.

**States.** A ``StateTrigger`` names the state — `hover`, `pressed`, `disabled`, `focused`, or an `attribute` with a name and value — and ``RoleStateMapping`` returns those. ``StateEmitter`` turns each into its selector: `:hover`, `:active`, `:disabled`, `:focus-visible` (`:focus-within` on a `textInput` or `select`, whose root is a wrapper `<div>` around the focused control) and `[data-name="value"]`. SwiftUI reads the same triggers as a button style's `isPressed`, `.onHover`, `isEnabled` and `isFocused` (a text field's own `@FocusState`), and an attribute as a typed value (*Roles and states*, below).

**Smart defaults.** A state the design does not draw falls back to a smart default, and a smart default is a list of ``StateEffect``s rather than property deltas: ``RoleStateMapping/smartEffects(for:)`` holds the one definition per trigger, and each emitter spells it. React's spelling, in `states.css`:

| Trigger | Effect | React | SwiftUI |
|---|---|---|---|
| `hover` | `dim(brightness: 0.95)` | `filter: brightness(0.95)` | `.colorMultiply(Color(white: 0.95))` |
| `pressed` (a link's `active` too) | `scale(factor: 0.98)` | `transform: scale(0.98)` — left out, with a warning, when the root is rotated or flipped | `.scaleEffect(0.98)` |
| `focused` | `focusRing(width: 2, offset: 2)` | `outline: 2px solid currentColor; outline-offset: 2px` | `.penFocusRing(…)`: a stroked overlay in the foreground style, following the root's corner radius |
| `disabled` | `fade(opacity: 0.5)`, `ignoresPointer` | `opacity: 0.5; pointer-events: none` | `.opacity(0.5)`, `.allowsHitTesting(false)` |
| `attribute` | none — the designer draws it | — | — |

SwiftUI writes each as one modifier that is the identity while its state does not hold (`.scaleEffect(state.contains(.pressed) ? 0.98 : 1)`), so every state's modifiers sit in one chain. Both emitters write from the effects alone, never from the state's name, so a state with no effects writes nothing.

**Designer deltas.** ``NodeDiffer`` records a designer's state as ``StateDelta``s whose ``PropertyChange/value`` is a ``DeltaValue``: the diff's pen-level encoding for most properties, and a typed ``DeltaTransform`` (rotation, `flipX`, `flipY`) for a turn or flip, so no target parses another's spelling. React spells a transform — the node's own and a state's alike — as CSS: Pen turns counter-clockwise and CSS's `rotate()` clockwise, so the angle is negated, and Pen flips before it turns, so the flips follow the turn (`rotate(-25deg) scaleX(-1)`); a state that is neither turned nor flipped writes `none`, and the custom property's base value is the node's own transform. Pen turns and flips a node about its `x`/`y`, so a node placed by its own coordinates (a child of a `layout: "none"` frame or of a group, or an absolutely positioned one) gets `transformOrigin: "0 0"` and draws exactly as Pen does; a node in a flex flow keeps CSS's centre pivot, and, since Pen's layout grows its slot to the turned bounds with the unturned box centred in it, a flowed node with a fixed width and height gets a margin of half the difference on each side (`margin: "16.569px 16.569px"` for an 80 × 80 box at 45°; negative along the side a box turned onto its side gives up), so its flex item is the turned bounds and later siblings sit where Pen's do (`render-transforms-and-effects` 35.845 → 0.634, CG 0.886; leaf `Mu4JsL`). A size CSS decides (fit content, fill) is not known when the code is written and gets no margin, nor does a line, whose margins centre its stroke. The one exception is a turned `fill_container` child: Pen fills its *unturned* box — the main-axis share, taken before any child is turned, or the container's inner cross size — and allocates the turned bounds, which flexbox cannot say, since a flex item's margins come out of the free space it shares. When every number that box depends on is in the document — the container's size on the filled axis, its padding and gap, and each sibling's main extent — `TurnedFillSizes` works it out and the child is written at that fixed size, so it gets the margins above; an unturned fill sharing the container with it is pinned to the same share, as Pen gives it. Otherwise (a container sized by its content or its parent, a sibling sized by its content, a variable) the child keeps the unturned slot of an ordinary fill and generating it warns (`render-turned-fill`, leaf `ozlazY`). `ReactTransformStateWebViewTests` holds a turned, a flipped and a turned-and-flipped `:disabled` state against Pen's export in WebKit (MAE under 0.04 on each board). SwiftUI draws a designer's state from its whole frame (``StateDefinition/variantNode``, kept for every designer's state) and reads no deltas.

**Paints.** The paint layer is internal to the module; each type states a Pen decision with no CSS in it, and React formats the result:

- `PaintRoute` picks nothing, one plain colour (a literal or a variable, with its blend mode), or layers.
- `GradientGeometry` is Pen's one map from a gradient's own unit space into the node's normalised box (`NormalizedPoint`), the renderer's gradient frame without CoreGraphics: `affineComponents` gives the map as a row-vector matrix, and the renderer's `PenFill.PenGradientFill.frameTransform(in:)` builds its `CGAffineTransform` straight from it, adding only the stretch to the node's box — one computation of the gradient's scale, rotation and centre, not two. Its `GradientGeometry+Screen` extension reads off what a target without Pen's map needs: a linear gradient's stop position as an affine function of the box point (`linearRamp`), an angular gradient's on-screen bearing at each turn on a stretched box (`angularBearing(atTurn:width:height:)`, and `keepsAngles` when the map is a similarity), and a radial ellipse's radii while it keeps to the box's axes (`axisAlignedRadii`). Start and end points for a linear gradient (`linearStart`, `linearEnd`) come from the same map, and so does the React SVG paint servers' `gradientTransform`.
- `MeshThemes` finds the theme combinations a mesh's colours depend on and resolves the fill under each.
- `StrokeRing` holds a stroke's width and outset per side for its alignment, as `EdgeLengths` of `SymbolicLength` — points plus multiples of variables, so a variable-bound width still halves and sums. `SymbolicLength+CSS.swift` writes them as `calc()`.
- `FillBox` is a fill's box with only its fixed sides known; React sizes a baked mesh raster from it.

### Emission

Emitters produce target-specific output files from analysis results. Pass ``ReactEmitter/Options`` to control behavior such as strict mode, and an optional ``PenDiagnosticCollector`` to capture warnings about inlined components.

- ``ReactEmitter`` generates a complete file set:
  - `components/*.tsx` — React + Tailwind component files with typed props and CSS variable references
  - `pages/*.tsx` — Page files that import and instantiate child components. A page declares no props of its own, but its root element is emitted through the same path a component root takes — `className={cn("…", className)}` and a `...style` spread — so it carries the same `<Name>Props` interface with an optional `className` and `style`, and a defaulted signature (`export function Home({ className, style }: HomeProps = {})`) so a router can still render `<Home />`. Both halves of the file set are pinned by goldens: components in `ReactEmitterTests` over `woodcase-app.pen`, pages in `ReactEmitterPageGoldenTests` over `Fixtures/pages.pen` (`woodcase-app.pen` marks every top-level frame reusable, so it detects no pages at all). Regenerate both with `UPDATE_GOLDEN=1 swift test --filter "ReactEmitter.*Tests"`
  - `ThemeProvider.tsx` — React context provider for theme axes
  - `lib/cn.ts` — Tailwind class merging utility
  - `theme.css` — CSS custom properties organized by theme axis selectors
  - `states.css` — CSS custom properties and pseudo-class rules for interactive states (only generated when components have states)
- ``ThemeEmitter`` generates the `theme.css` file with CSS custom properties.
- ``StateEmitter`` generates the `states.css` file containing state-driven CSS. Designer-override states use CSS custom properties (`var()` substitution in inline styles) with pseudo-class or data-attribute selectors. Smart-default states emit their ``StateEffect``s as direct CSS properties (e.g., `filter: brightness(0.95)` for hover's dim; see *Smart defaults* above). Components with roles get semantic HTML elements (`<button>`, `<a>`, `<nav>`) and `wc-*` CSS classes. Structural states (variants with added/removed children) emit separate render functions with a ternary dispatch wrapper. The `tabBar` role uses N-way string dispatch (`selected?: "home" | "log"`) instead of boolean state props, and emits `<nav role="tablist">` as the root element. Tab bar variants — siblings matching the `{Name}:{state}` naming convention — are merged into a single component regardless of their reusable status, and screen refs to variant IDs resolve to `<TabBar selected="stateName" />`.

```swift
let diagnostics = PenDiagnosticCollector()
let result = ReactEmitter.emit(
    document: doc, components: components, pages: pages, theme: theme,
    options: ReactEmitter.Options(strict: false), diagnostics: diagnostics
)
// result.files — the generated source files
// result.iconLibraries — icon library families used (e.g. "lucide", "phosphor")
// result.imageAssetURLs — relative image URLs referenced by components
```

**Connections.** A `connection` emits nothing: Pen allows one only at the top level, between artboards, where no page or component markup reaches, and one found inside a frame is skipped rather than reported as unsupported.

**Sizing.** A fixed side is its number, `fit_content` is `"fit-content"` and `fill_container` is `"100%"` (in a column, `flex: 1` for the height) — except where CSS would not land on Pen's size (`ChildPlacement`, `ReactEmitter+Sizing.swift`):

- `fit_content(N)` with nothing to fit — a frame with no flowed child (absolute children do not count) and no padding on that side, or a shape — is `N`; CSS's `fit-content` would collapse it to 0.
- `fill_container(N)` on a node placed by its own `x`/`y` — a child of a `layout: "none"` frame or of a group, or an absolute child — is `N`: Pen gives such a node no container to fill, and CSS's `100%` would resolve against the shrink-wrapped wrapper and draw nothing.
- A `layout: "none"` frame never fits its children (Ben's ruling, 2026-09-27): an unsized side is 0, a `fit_content` side its fallback or 0; its children still draw, overhanging it.
- A flowed frame with no size on its container's cross axis — no height in a row, no width in a column — is written `"fit-content"`: Pen's `alignItems` has no stretch, where CSS's default `align-items: stretch` would stretch it to the row (`layout-deep-nesting`).

**Browser nodes.** A `browser` node becomes an `<iframe>` (ruling, Ben, 2026-09-26): `src` is ``PenNode/BrowserData/pageURL``, the stored address with the `https://` Pen strips restored, and is omitted when the node has none; `title` is the node's name, then that address, then `browser`. It is sized and styled like a rectangle, with `border: "none"` and `overflow: "hidden"`. `deviceId`, `zoom` and the scroll offsets are not emitted: the frame's size is already the viewport, and a cross-origin page's zoom and scroll cannot be set from outside it.

**Mesh gradients.** CSS has no mesh primitive, so a `mesh_gradient` fill on a frame, rectangle or CSS ellipse is baked to a small PNG (ruling, Ben, 2026-09-26: a pre-rendered raster). The pure-Swift mesh core (<doc:PenMeshGradients>) rasterizes it at ``ReactEmitter/Options/meshRasterScale`` pixels per point of the box — 2 by default, a Retina display's density — scaled down to 1024 px on the long side for a very large box, or at 64 × 64 when a side is not fixed; ``PortablePNGEncoder`` writes the PNG without CoreGraphics, so the emitter still builds on Linux. The fill's own opacity is folded into the raster's alpha. The raster becomes one layer of the element's `background`, stretched over the box, in the fill stack's order like any other layer:

```tsx
background: "url('data:image/png;base64,…') center / 100% 100% no-repeat, #FFFFFF",
```

A mesh whose colours (or opacity) reach a themed variable, directly or through a chain, is baked once per combination of the theme axes it depends on. The layer then reads `var(--wc-mesh-<hash>)`, and `theme.css` declares that property under `:root` for the default theme and under `[data-axis="option"]` for each other one, exactly as it does for themed colours, so switching the theme swaps the raster. A mesh with only literal or unthemed colours is inlined. A mesh Pen would not draw — a missing `columns`, `rows`, `points` or `colors`, or a count that does not match the grid — emits no layer. Text and strokes take the same raster (below); a themed mesh on an SVG-drawn stroke does not, because an SVG pattern cannot read a custom property.

The raster was 64 px on the long side until leaf `3n7gRZ`: a smooth mesh loses little at that size (a mean absolute error of 0.33–0.68 of an 8-bit step after upscaling, `project/2026-09-26-mesh-gradients.md` §3), but a fold's edge and a transparent patch's edge stepped at the browser's 2x (`ReactRenderWebViewTests`' `render-mesh-gradients-mfold` and malformed-point boards, 1.3–2.7, now 0.30–0.60 and each equal to CG). The cost is source size: a 240 × 180 box's raster is about 118 KB of base64 at 2x, against 5 KB at 64 px (the `MeshSwatch` golden); lower `meshRasterScale` where that matters more than the edges. The goldens in `Fixtures/golden/mesh/` pin both forms over `Fixtures/react-mesh.pen`.

**Gradient geometry.** A gradient's `opacity` is baked into its stops' alpha (`#RRGGBBAA`, or `color-mix(in srgb, var(--x) 50%, transparent)` for a variable). Pen lays every gradient out in the node's normalised box (`GradientGeometry`), and the CSS states that geometry exactly on a box of any size, including one sized at layout time (`ReactEmitter.cssGradient(_:box:outsets:)`):

- A **linear** gradient along one of the box's axes keeps its angle, `linear-gradient(<−rotation>deg, …)`, with its stops moved to where `center` and `size` put them (`0deg, #F00 20%, #00F 120%` for a centre at y 0.3). An **off-axis** one cannot use an angle: Pen's isolines are fixed in the normalised box, so they slant with the box's proportions, and a CSS angle runs corner to corner. It uses a corner keyword instead — `to top left`, whose isolines CSS lays parallel to the tile's other diagonal, an affine rule — on a tile whose proportions, in the box's own percentages, carry Pen's slant, centred on the box and covering it (`center / 173.205% 100% no-repeat`), with the stops placed along the tile's line where Pen's ramp puts them. A plain 45° gradient needs no tile: `linear-gradient(to top left, #F00 14.645%, #00F 85.355%)`, its one-unit line shorter than CSS's corner-to-corner one.
- A **radial** gradient reaches radius ½ of its `size` around its `center`, so its default is CSS's `closest-side`. While its ellipse keeps to the box's axes — unturned, a quarter turn (the radii swap), or a circle in the unit box — it is a CSS ellipse. A turned ellipse, which CSS cannot draw, is an SVG image: a `radialGradient` with Pen's map as its `gradientTransform` in a `0 0 1 1` view box stretched over the tile with `preserveAspectRatio="none"`, as a base64 `data:` URL. An SVG image cannot read the page's custom properties, so a turned ellipse with a variable stop keeps the unturned CSS ellipse.
- An **angular** gradient is a `conic-gradient` about Pen's centre, started `from` Pen's turn 0 (Pen turns counter-clockwise, CSS clockwise). On a box where the map keeps angles (a square and an even `size`) Pen's stops are its own; on a stretched box the turns bend, which a conic gradient cannot express, so it is sampled at its stops and 90 equal turns, each at its on-screen bearing with the colour Pen's ramp has there (a `color-mix()` between variable stops). A box with a side that is not fixed — auto-height text, say — counts as square.

An SVG paint server (below) uses Pen's map directly — the unit gradient through a `gradientTransform` matrix — so on SVG a turned, off-centre or resized gradient keeps Pen's geometry too.

**Paints on text.** A text node whose fills are one enabled colour emits `color`, as before. A text or icon with no enabled paint — no `fill`, an empty list, only disabled fills — writes `color: "transparent"` (an icon's `color="transparent"`): Pen draws it as nothing, where an element with no colour would inherit the page's black. An icon is painted with its topmost enabled fill the emitter can write, skipping a disabled one: a solid is the component's `color`; a gradient, an image or a mesh is drawn through the glyph, as Pen draws it, by an SVG paint server (below) laid out over the component's `viewBox` — which the component scales onto the node's box — named on the attribute the library paints its glyph with (`stroke` for lucide and feather, `fill` for phosphor and Material Symbols) and defined in a hidden zero-size `<svg>` beside the icon, the two in a fragment. `ReactIconPaintWebViewTests` renders the `gradient` and `image` boards against Pen's exports with lucide's real `Square` in place of the harness's stub: 2.12 and 1.98, against 4.57 and 4.41 with the icon black (both include the harness's serif fallback for the text). An enabled solid whose literal is not a colour (`#zzzzzz`) is written `#000000`, as Pen draws it black; on text, a colour variable the document does not define is an undefined custom property, and CSS falls back to the inherited colour, black on an emitted page. `ReactUnfilledPaintWebViewTests` renders `render-text-unfilled.pen` in WebKit against Pen's exports. Any other paint — a gradient, an image, a mesh, a stack — follows Pen, whose paint domain for text is the node's box (`project/2026-09-26-text-and-stroke-fills.md`, findings 1 and 6): every enabled fill becomes a background layer over the text's own box, top fill first (a colour as `linear-gradient(c, c)`), shown only through the glyphs.

```tsx
backgroundImage: "linear-gradient(-270deg, #FF0000 0%, #0000FF 100%), linear-gradient(#00FF00, #00FF00)",
backgroundSize: "100% 100%",
backgroundPosition: "center",
backgroundRepeat: "no-repeat",
backgroundBlendMode: "multiply, normal",
backgroundClip: "text",
WebkitBackgroundClip: "text",
WebkitTextFillColor: "transparent",
color: "transparent",
```

Image fills size their layer `cover`, `contain` or `100% 100%` by mode. Fill blend modes in a stack become `background-blend-mode`; a lone blended fill (or a lone blended colour) becomes the element's `mix-blend-mode`, unless the node has a blend mode of its own. Auto-width painted text gets `width: "fit-content"`, so a stretching flex parent cannot widen the box the paint spans. A shader alone paints nothing (`color: "transparent"`), as on shapes, and on an icon too. Underline and strikethrough take `color`, so on painted text they are transparent — Pen strips both from text anyway (`woodcase lint` reports them).

**Where a plain stroke sits.** A stroke that is one enabled colour of normal blend is a plain declaration, placed where Pen places it without taking layout space: on a rectangle, frame or CSS ellipse an inner stroke is an inset box-shadow, a centred one an inset box-shadow of half the width beside a spread one of the other half (`boxShadow: "inset 0 0 0 4px #F00, 0 0 0 4px #F00"`), so it straddles the edge, and an outer one a spread box-shadow (`0 0 0 8px #F00`); an absent width is Pen's default of 1. Until leaf `Mu4JsL` an outer stroke was an `outline`, which WebKit draws nothing of around a 0×0 box, where Pen paints the band about the point: an 8 pt outer stroke is a 16 × 16 square, a centred one 8 × 8, an inner one nothing (`render-stroke-bands`, `render-sizeless-frames-paint` 0.329 → 0.018). The stroke's box-shadows come before the node's own shadows, since CSS paints the first on top and Pen draws the stroke over them. A per-side stroke of any alignment is drawn by the overlay below: an inner one was a border per side until leaf `Mu4JsL`, which moved the frame's children in by its widths and painted over them, where Pen moves no child and draws its stroke beneath them (`render-inner-sides`, 5.6–12.9 → 0.000). A line with no enabled stroke paint draws nothing, as Pen draws nothing; it had drawn `currentColor` (`render-unstroked-lines`). An SVG shape takes a `stroke` attribute with its `strokeLinecap` and `strokeLinejoin` when they are not the default (butt, miter), and, when its `viewBox` stretches it onto the box, `vectorEffect="non-scaling-stroke"`, because the renderer strokes the mapped outline at the stroke's own width. A line's SVG runs from its box's top-left corner to its bottom-right as the renderer draws it, grown by half the stroke on every side (`viewBox="-6 -6 152 12"`) and pulled back by `margin: -6`, so the stroke centres on the line; a full-width line's `borderTop` gets `marginTop` and `marginBottom` that do the same. A full-width line whose stroke one colour cannot carry — a gradient, an image, a stack, a blended colour — is instead a band as tall as the stroke, painted by the stroke's fills as a background and pulled back by the same margins; it had drawn `currentColor` (leaf `4fZZ38`). A flat line's box has no height, so its paint is laid over the stroke's band, fixed or full-width alike: a paint server over the zero-height box itself had a singular transform and drew nothing (`render-painted-lines-fixed`, 1.753 → 0.011). Pen lays the paint over the zero-height box and collapses a ramp with any component across the line — a slanted one to its two end colours split at the line, a vertical or radial one to black; React, the renderer and SwiftUI all paint the ramp across the band as it is meant, a kept divergence (<doc:PenInteroperability>, *Kept Divergences*; `render-painted-lines-fill-degenerate` measures 16.296 in React, CG 16.297, so it gates at CG + 1.0). A stack of fills on any CSS box writes a colour above the bottom layer as a flat `linear-gradient(c, c)`, since CSS drops a whole `background` list with a bare colour in any layer but the last, and names each layer's blend mode by its CSS name (`color-burn`, not `colorBurn`). An arc, pie slice or ring is an SVG path written from the renderer's own outline (``PenShapeGeometry``, as SVG path data by `PenShapeOutline.svgPathData(number:)`).

**Paints on strokes.** Any stroke that is not one plain colour is drawn the way Pen draws it — clipped to the stroke, laid out over the node's box whatever the alignment, gradients padded beyond the box and images drawn nowhere but on it (`project/2026-09-26-text-and-stroke-fills.md`, finding 2):

- **Rectangles, frames and CSS ellipses** get an absolutely positioned overlay `<div aria-hidden="true">` — as does a plain colour on per-side widths, painted as one colour layer. A transparent border as wide as the stroke's outer reach (0, ½ or all of the width for inner, centre and outer; per side for per-side widths, which honour `strokeAlignment` with centre as the default) makes its padding box the node's box, where image and mesh layers are placed (`backgroundOrigin: "padding-box"`); padding for the rest of the width makes its content box the stroke's inner edge, which `mask: linear-gradient(#000 0 0) content-box exclude, linear-gradient(#000 0 0)` cuts out. Its radii are the node's grown by the outset, so the ring follows rounded corners. Gradient layers span the whole overlay (`border-box`) with their geometry pulled back onto the node's box — an axis linear gradient's stops moved in by the growth at each end of its line, `calc(4px + (100% - 8px) * 0.25)`; a radial gradient's ellipse and an angular gradient's centre on the node's box; an off-axis linear gradient's tile, or a turned ellipse's SVG image, centred on the node's box and grown past it far enough to reach the stroke's outer edge (`calc((100% - 8px) * 1.06667)`; three boxes when the box or the stroke is not a fixed number) — so CSS pads them past the box as Pen does. The host gets `position: relative`; a frame with children also gets `isolation: isolate` and the overlay `zIndex: -1`, so it paints under the children, as Pen draws a container's stroke before them.
- **Paths, polygons, arc and donut ellipses and SVG lines** stroke with `url(#wc-paint-…)` paint servers in `userSpaceOnUse`: a gradient, or a pattern holding an image or mesh raster once over the node's box inside a tile large enough that the stroke's overhang shows nothing. A stack draws one stroked copy per layer, bottom first, blend modes as `mix-blend-mode`. An inner stroke is drawn at twice the width and clipped to the shape, an outer one at twice the width and masked by it — a solid colour placed inside or outside the outline too, which an SVG `stroke` attribute cannot place. An angular gradient, which SVG has no paint server for, is the same `conic-gradient` a CSS box takes, as the background of a `<div>` in a `foreignObject` over the box grown by the overhang, inside a `<g>` masked by the shape stroked white at the drawn width (and, for an inner or outer stroke, a `<g>` clipped or masked by the shape around that); the mask sits on the group because WebKit cuts a masked `foreignObject` off at the SVG's top-left corner (`render-angular-shapes`, strokes 5.1–9.0 → 0.04–0.09, CG 0.03–0.06; leaf `Mu4JsL`). The `<svg>` of any stroked shape gets `overflow="visible"` so a centred or outer stroke is not cut at the node's box. Ids are hashes of the node and the definition, so repeated emissions agree.

**Paints on SVG fills.** The same paint servers fill these shapes: a fill that is not one plain colour — a gradient, an image, a mesh, a stack, a blended colour — is one filled copy of the shape per layer, bottom first, laid out over the node's box (a path's viewBox or tight bounds), Pen's fill domain as for a stroke; the strokes are drawn over them (`render-fill-domains`, each board within 0.003 of CG; it drew `fill="none"` before, 7.8–31.9). An angular gradient fill is the conic `foreignObject` above inside a `<g>` clipped to the shape, with its fill rule (`render-angular-shapes` fills 18.6–24.2 → 0.10–0.16, CG 0.04–0.09). A path with no `viewBox` names its tight bounds as the SVG's `viewBox` with `preserveAspectRatio="none"`, since Pen maps those bounds onto the box (``PenPath/sourceRegion(viewBox:)``); geometry that already spans its box keeps `0 0 w h`.

**Per-side widths on shapes.** An ellipse, a polygon, a path or a line takes a per-side `strokeWidth` as Pen draws it, one uniform stroke of the `top` width (``PenStrokable/drawn(on:)``; `render-per-side-shapes.pen`): an SVG `strokeWidth`, or a CSS ellipse's box-shadows.

Not covered: a painted stroke on a `browser` node (an `<iframe>` cannot hold the overlay); themed meshes on SVG strokes; an angular gradient through an icon's glyph; an outer or centred painted stroke on a frame with `clip`, whose `overflow: hidden` cuts the overlay's outer band; and a painted stroke's state overrides. The goldens in `Fixtures/golden/paints/` pin gradient and stacked text, a rounded outer ring, a path and a per-side image stroke over `Fixtures/react-paints.pen`, and `ReactPaintWebViewTests` renders the emitted React for `render-stroke-fills.pen` and `render-text-fills.pen` in WebKit against Pen's own exports.

**Fills on SVG shapes.** A path, polygon, arc or donut whose fills are one plain colour takes its topmost enabled solid as its `fill` attribute, skipping a disabled one — the rule text and icons follow; any other fill is drawn in layers, as *Paints on SVG fills* above says.

**Text layout.** A text's lines are set as Pen sets them (``ReactEmitter``'s `textLayoutStyles`; leaves `Gmh2sB`, `3Xbv46`, `RgeMUN`):

- **Line height.** An explicit `lineHeight` stays a multiple of the font size. With none, Pen sets each line at the font's natural pitch — ascent, descent and leading rounded to a whole point, ``PenTextMeasurer/naturalLineHeight(of:)``, the pitch the renderer and SwiftUI use — so React writes that pitch in px at generate time (`lineHeight: "19px"` for Inter 16). It is measured on the font this machine resolves, so it is written only for a family Core Text has, named as a literal or by a variable that holds the same family under every theme (the size likewise, 16 when unset); a text with no family, a family or size that changes with the theme, or a family this machine lacks gets `lineHeight: "normal"` — the font's own ascent, descent and line gap, unrounded, in the browser. Before, every such text was `lineHeight: 1.3`. An empty text reserves one line at the pitch it would have (`minHeight`), or none where it is `normal`, since its `&nbsp;` already holds the browser's line.
- **Optical size.** Every text writes `fontOpticalSizing: "none"`: Pen draws a variable font at its default optical size whatever the point size, where a browser moves the `opsz` axis with it and sets Inter above 14 pt in its narrower display cut (<doc:PenGoogleFonts>). It is written on the text rather than once in `theme.css`, so a component used without the stylesheet keeps it.
- **Newlines and wrapping.** `whiteSpace: "pre"` for a text Pen does not wrap — an `auto` (or absent) growth whose width is `fit_content` or unset, as `PenLayoutEngine` measures it — so it stays on one line per newline and never shrinks in a flex row; `whiteSpace: "pre-wrap"` for any other, which wraps at its width and keeps its newlines and spaces. Content holding a newline, a brace, an angle bracket or an ampersand is written as a string expression, `{"Line one\nLine two"}`, since JSX collapses a line break in bare text and reads the others as syntax.
- **Vertical alignment.** `textAlignVertical: "middle"` or `"bottom"` makes the element a column (`display: "flex"`, `flexDirection: "column"`) that centres or sinks its lines (`justifyContent: "center"` or `"flex-end"`); `top` is the normal flow and writes nothing.
- **First baseline.** CSS puts a text's first baseline at `ascent + (line-height − ascent − descent) / 2` and a browser snaps it to a device pixel; Pen puts it on a whole point (``PenTextMeasurer/firstBaseline(of:lineHeight:pitch:)``). IBM Plex Sans at 13 pt on its 17 pt line is 13.375 in CSS and 13 in Pen, 27 px against 26 at 2x; Inter at 16 pt is 15.32 against 16. So a top-aligned text whose font is known here (as for the pitch above) writes the difference as a margin pair, `marginTop: -0.375, marginBottom: 0.375`, which moves the element without changing its margin box — its place in a flex or block flow, and so the layout, stay as they were — and without the stacking context `position` or `transform` would add. Middle and bottom alignment keep the browser's baseline, not yet measured against Pen (leaf `BpaSrF`: every `layout-text-*` text had sat a pixel low; see the re-measure above).

**Effects.** A node's effects follow the renderer's rules (<doc:PenRendering>, *Effects*): every enabled shadow, in array order — the first drawn at the bottom — and the first enabled layer blur and background blur with a radius (``ReactEmitter``'s `NodeEffects`; leaf `0M8jRo`).

- **CSS boxes** — frames, rectangles, CSS ellipses, browsers — take one `boxShadow` list. CSS paints the first entry on top and Pen the last, and Pen draws the stroke over its inner shadows, so the list is the stroke's own shadows, then the inner shadows top first, then the outer shadows top first. A shadow's `blur` passes through: a box shadow's blur radius is twice its Gaussian's sigma, as Pen's is. Pen casts an outer shadow from the shape grown by the stroke's reach past it (``PenShadowSilhouette``; `render-stroke-bands`), so each outer shadow — or blended shadow layer — spreads by that reach: the whole width for an outer stroke, half for a centred one, none for an inner one or a stroke with nothing to paint (`10px 10px 8px 12px #FFF` under a 12 pt outer stroke). A per-side stroke's band, which a uniform spread cannot follow, spreads nothing.
- **Text** casts its outer shadows from its glyphs: `textShadow`, top first, the blur passed through. Painted text — shown through `background-clip: text` — takes `drop-shadow()`s instead, since a text shadow is painted over the element's background and would cover the clipped paint. CSS has no inner text shadow; a text's inner shadows are not written, and generating one warns once per node in each file: `React draws no inner shadow on text: CSS has no inset text shadow` — a CSS limit Ben ruled to keep (2026-09-27) over an SVG `<text>` filter or a layered approximation.
- **Icons, SVG shapes** (paths, polygons, lines, arcs and donuts) **and groups** take one `filter` of `drop-shadow()`s, top first, cast by what the element paints. A `drop-shadow`'s blur length is the Gaussian's standard deviation, so it is half of Pen's `blur` (WebKit drew `drop-shadow(8px 10px 12px …)` twice as soft as Pen's `blur: 12`: `render-group-shadows-group-outer` measured 2.496 against Pen's export, 0.482 at 6px). A group's shadow is therefore an approximation of Pen's silhouette: a translucent child casts a fainter shadow that shows through it where Pen's is knocked out, and a line, a child's own shadow and a frame child's overhanging children cast one too; and each `drop-shadow` also shadows the ones applied before it. A group's inner shadow is not written, and generating one warns once per node in each file: `React draws no inner shadow on a group: CSS has none for painted content`. Both are CSS limits Ben ruled to keep (2026-09-27): an SVG-filter silhouette matched Pen almost exactly but WebKit's filter regions were fragile (leaf `0M8jRo`).
- **Inner shadows on SVG shapes and icons** are SVG filters (leaf `4fZZ38`). The filter floods its region, cuts the silhouette out of it — the outside, which casts the shadow inward — offsets and blurs that (σ, half of Pen's `blur`), colours it with the shadow's colour and keeps it where the silhouette covers, in sRGB. An SVG shape (path, polygon, arc, donut) draws one copy of itself per inner shadow, filled black and filtered to the shadow alone, between its fill and its stroke, as Pen orders them; the fill is then its own element rather than riding on the stroke's, and under a stretching `viewBox` the filter's offset and deviation are divided by the stretch on each axis. An icon's inner shadows are `url(#…)` filters at the head of its CSS `filter`, before its `drop-shadow()`s, each compositing the shadow over the glyph, defined in a hidden `<svg>` beside it. A blended inner shadow keeps its blend mode: the shape's copy takes `mixBlendMode`, the icon's filter an `feBlend` against the glyph. The flood matters: inverting the silhouette's alpha instead (`feComponentTransfer`) lost every edge on the silhouette's bounding box, since WebKit inverts only inside it (a hexagon measured 1.721 against Pen's export that way, 0.036 this way). Measured 2026-09-28 with `swift test -j 3 --filter ReactRenderWebViewTests` on `render-inner-shadow-shapes` (`scripts/gen-react-fx-fixtures`, then `scripts/pen-oracle --scale 2`): the eight shape boards 0.022–0.151 and the three icon boards 0.050–0.290. The same leaf gave the renderer icon inner shadows and an even-odd clip for a ring's (CG 0.056–0.655, `PenInnerShadowShapesSnapshotTests`; the icons had none, 1.365–3.913, and the donut's hole filled black, 19.971). A line has no inside, and Pen draws it no inner shadow; neither does React, without a warning.
- **Layer blur** is `blur()` at half its radius, fraction kept (`blur(2.5px)` for 5), in the same `filter` after the shadows, as Pen blurs a node with its shadows. Before, the radius was truncated to a whole pixel and a second blur wrote a second `filter` key.
- **Background blur** is `backdropFilter` and `WebkitBackdropFilter` at half its radius, only on a CSS box with a visible fill (``PenFills/hasVisiblePaint``; a browser always has its placeholder's): Pen draws none through a node without one. It is not written on text, icons or SVG shapes, whose box is not their shape.
- **Blend modes.** CSS blends an element, not one entry of its shadow list, so when an outer shadow on a rectangle, a CSS ellipse or a frame without `clip` is blended, all of that node's outer shadows move to layers of their own: one absolutely positioned `<div aria-hidden="true">` per shadow, first child of the node, with the node's corner radii, the shadow as its `boxShadow` and its `mixBlendMode`, in array order so they keep Pen's stacking; the node gets `position: relative`. Being positioned, a layer paints over later siblings that are not, where Pen draws those over the shadow. A blended shadow anywhere else — an inner shadow on a CSS box, a shadow on text, an outer shadow on an icon, an SVG shape, a group, a browser or a clipping frame — is drawn without its blend mode, with a warning, once per node in each file: `React draws this node's blended shadow without its blend mode`. An inner shadow on an icon or an SVG shape is drawn blended; one on text or a group is left out and named by its own warning alone, so a node gets at most one warning per unsupported shadow.

**Shader fills.** Pen runs a shader fill — uniforms, samplers, `@sdf`, `@backdrop`, on shapes, text and icons alike (`render-shader-fills.pen`) — and no Woodcase target does. React writes nothing for one, wherever it sits, and warns once per node in each file, `React does not emit shader fills yet`: SwiftUI's wording for the same gap (below). `woodcase lint` reports each one (`shader-not-drawn`), and `render` and `shot` warn once per document (<doc:PenRendering>). See finding F1 of `project/2026-09-27-fidelity-gaps.md`.

### Icon Libraries

``IconLibraryMapping`` resolves icon font family names to their React npm package details. It supports Lucide, Feather, Phosphor, and Material Symbols (Outlined, Rounded, Sharp). Each icon is mapped to its correct component name, import path, and any extra props (e.g. Phosphor weight variants).

A Material Symbols icon is drawn at Pen's weight: the node's `weight`, else 200, the only axis Pen's `getIconPath` sets. `@nine-thirty-five/material-symbols-react` takes no weight prop — each weight is its own import path, `…/{style}[/{weight}]`, 100 to 700 in steps of 100, the bare style path being 400 (its README, version 2.4.4) — so the weight picks the path: `import { VpnLock } from "@nine-thirty-five/material-symbols-react/outlined/200"`. A weight between steps is drawn at the nearest, with a warning; one icon at two weights of one style is imported twice, the second under its weight (`VpnLock as VpnLock700`). The harness's icon stubs set the `wght` their import path names, as the package's glyphs would be (`parser-icon-font` 2.953 → 0.410, leaf `AyTAji`).

### Font Loading

``FontsourceMapping`` maps font family names to Fontsource npm packages. When packaging output, font dependencies are automatically included in `package.json` and CSS `@import` statements are prepended to `theme.css`.

### Manifest

``ManifestEmitter`` generates a `manifest.json` file containing component metadata,
theme axes, and variable definitions. The manifest is included automatically in
every emit — it uses ``GeneratedFile/WritePolicy/always`` so it always reflects the
current design state. The manifest format is simple JSON consumable by the viewer,
documentation generators, or other external tools:

```json
{
  "components": [
    { "name": "ActionButton", "path": "components/ActionButton", "props": [...] }
  ],
  "pages": [
    { "name": "Home", "path": "pages/Home" }
  ],
  "theme": {
    "axes": [{ "name": "mode", "values": ["light", "dark"] }],
    "variables": [{ "name": "accent", "type": "color", "values": { "default": "#C67A52", "mode:dark": "#D4895F" } }]
  }
}
```

### Packaging

``PackageScaffolder`` wraps emitted files in an npm package structure. It relocates
source files under `src/`, generates a barrel `index.ts` that re-exports all
components and pages, and produces scaffold files (`package.json`, `tsup.config.ts`)
with a ``GeneratedFile/WritePolicy/scaffoldOnce`` policy so they are only created
if missing — preserving any manual customizations on re-generation.

```swift
let options = PackageScaffolder.Options(packageName: "@myorg/ui")
let packaged = PackageScaffolder.scaffold(files: files, options: options)
```

### Preview Viewer

``ViewerScaffolder`` generates a `viewer/` directory containing a Vite + React app
for browsing generated components and inspecting theme variables. It reads the
manifest at runtime to populate a sidebar with components, pages, and a variable
matrix table. Theme axis selectors set `data-*` attributes on preview containers
so components render with the correct theme.

All viewer files use ``GeneratedFile/WritePolicy/scaffoldOnce`` except
`viewer/components.ts`, which is regenerated on each run to match the current
component and page list. Viewer templates are stored as bundled resources in
`CodeGen/ViewerTemplates/` and loaded at runtime through ``WoodcaseResources``, so
`scaffold` throws ``WoodcaseResources/Missing`` when the resource bundle is not installed.

```swift
let viewerFiles = try ViewerScaffolder.scaffold(
    components: components, pages: pages, packageName: "@myorg/ui"
)
```

### SwiftUI

``SwiftUIEmitter`` is the second target. It takes the same analysis results through the same `emit(document:components:pages:theme:options:diagnostics:)` shape as React, and writes a SwiftPM package a person can build, run and depend on as it is — its views, its theme, a catalog of the kit with an executable that opens it, and every image, icon font and text font the views draw:

```
Package.swift                                   rewritten on every run: the library, which processes Resources/, and <Module>Catalog
Sources/<Module>/Components/<Component>.swift   one public View per reusable component
Sources/<Module>/Pages/<Page>.swift             one public View per page
Sources/<Module>/Theme/PenTheme.swift           the themes and variables, when the document has any
Sources/<Module>/Theme/PenTheme+Environment.swift  the theme in the environment, penTheme(…), PenThemeReader
Sources/<Module>/Support/PenSupport*.swift      the helpers the views use, PenFonts among them
Sources/<Module>/Catalog/PenCatalog*.swift      the kit's catalog: PenCatalog, PenCatalogSheet, PenCatalogThemes
Sources/<Module>Catalog/main.swift              the <Module>Catalog executable: a window, --snapshot or --fonts
Sources/<Module>/Resources/.gitkeep             keeps the directory Package.swift declares, even when it holds nothing else
Sources/<Module>/Resources/<image>              every local image a fill or stroke uses (copied by the CLI)
Sources/<Module>/Resources/<icon font>.ttf      every icon library's font (copied by the CLI)
Sources/<Module>/Resources/<text font>.ttf      the file of every text face drawn whose family the OS does not ship (copied by the CLI)
```

`woodcase generate swiftui design.pen --output ui --name AcmeUI` writes it; `swift build` in `ui` builds it, `swift run AcmeUICatalog` opens the catalog, and `woodcase help codegen` is the same ground in the terminal. Every SDK API the package calls is on a checked list, audited against both floors (<doc:SwiftUIChurn>). `SwiftUIPackageBuildTests` generates `woodcase-app.pen`'s package through the CLI, builds it with `swift build` and checks with `--fonts` that every bundled font registers.

**The manifest.** `Package.swift` is a function of `--name` and `--floor` alone, so it is rewritten on every run like every other file (``GeneratedFile/WritePolicy/always``), never left stale by a new floor or a document that gains its first image or font. It always declares `resources: [.process("Resources")]` — which is what gives the module `Bundle.module` — and the emitter always writes `Resources/.gitkeep`, because SwiftPM refuses a declared resource directory that does not exist and version control drops an empty one. The package is meant to be depended on (`.package(path: "ui")`), not edited; a person's own targets go in a package of their own.

**Fonts.** ``EmitResult/fontFaces`` names every text face the views set — each family at each weight and style it is drawn in, the family a literal `fontFamily` or every value a family variable takes under any theme (`woodcase-app`'s `$font-primary` is IBM Plex Sans, at 400, 500 and 600). `woodcase generate swiftui` asks ``GoogleFontResolver/fontBundle(for:declaredIn:relativeTo:)`` for their files, by the renderer's own chain, so the package draws in the faces `woodcase render` draws with: a family the document declares (``PenDocument/fonts``) is its declared files; a family the OS ships (resolved from `/System/` or `/Library/Apple/`) is left to the system; any other family is the Google Fonts file of each face drawn (<doc:PenGoogleFonts>, *Faces*), from the cache or downloaded into it — and no file of a face nothing draws. A family installed on this machine but not shipped with the OS is still taken from Google Fonts, never copied from the machine's own fonts: a person's licensed font is not the package's to redistribute. A family with no file is a warning, and the package draws it in whatever the system has. The support file `PenSupport+Fonts.swift` declares `public enum PenFonts`, which registers every `.ttf`, `.otf` and `.ttc` in `Bundle.module` with `CTFontManagerRegisterFontsForURL` — from the file, never from bytes, which Core Text silently refuses (`project/gotchas.md`) — once, the first time `PenFonts.faces` is read. The views read it themselves: `penFont`'s face registers before it resolves a family, and `PenIconShape` finds its glyphs' font through `PenFonts`, so icon and text fonts share one registration and nothing has to be called before the package's views draw — in an app, a preview or the catalog. An app calls `PenFonts.register()` only to set a bundled family in views of its own before any of the package's has drawn. `swift run <Module>Catalog --fonts` prints `registered` or `failed`, the family and the file for each bundled font, and exits 1 when Core Text refused one.

**What it writes.** Frames, groups, rectangles, ellipses, arcs and donuts, polygons, paths, lines, icons and text, with their paints, strokes, effects, transforms and node blend modes (below), and reusable components and their instances (*Components and instances*, below). Every other node (a browser…) is a marked placeholder — a `// woodcase: <type> "<name>" is not emitted yet` comment over a `Color.clear` of the node's size — plus a warning; a property the emitter does not draw yet (a shader fill — `SwiftUI does not emit shader fills yet`, as React words it — or a variable the document does not define) is a warning and the node is drawn without it. Variables are read through the document's theme (*Themes*, below). A component's slots are `@ViewBuilder` parameters (*Slots*, below).

**Previews and the catalog.** Every component and page file ends with a `#Preview` per state a caller can pin (*Roles and states*, below), each repeated under every theme option other than the default, one axis at a time — `#Preview("pressed, mode: dark")` is the pressed call under `.penTheme(mode: .dark)`. One axis at a time, not every combination: the sum of the axes' options stays small where their product does not, and the catalog's pickers reach every combination. The package also carries the SwiftUI counterpart of React's kit page (``ViewerScaffolder``), written by `SwiftUICatalog`: `PenCatalogSheet` draws every component in each of those states, every page, a swatch per colour token, the value of every other token and a line in every text style the document sets, largest first, all under the environment's theme; `PenCatalog` shows the sheet in a scroll view of both axes with a toolbar picker per theme axis; `PenCatalogThemes` sets the sheet side by side under every theme variant. `Package.swift` declares a `<Module>Catalog` executable, so `swift run <Module>Catalog` opens the catalog in a window on macOS with no Xcode project, and `swift run <Module>Catalog --snapshot kit.png` renders `PenCatalogThemes` to a PNG — at 2x, or as near it as keeps the bitmap under the 16,384 pixels a side `ImageRenderer` draws (the `woodcase-app` kit is 3,780 × 8,910 points). The catalog's pieces and layout are the support files `PenSupport+Catalog.swift` and `PenSupport+CatalogLayout.swift`: every specimen is drawn at its ideal size, never squeezed, and rows wrap at the window's width (at 1,200 points in a snapshot), so a specimen wider than the window is the only thing the window scrolls sideways for. Verified 2026-09-27 on the emitted `woodcase-app` package by hosting `PenCatalog` in windows 1,400, 900 and 480 points wide and scrolling its `NSScrollView` with in-process wheel events: each reached the right edge and the bottom. The catalog's type names and the support files' are reserved, so a component named `PenCatalog` is `PenCatalogView`.

**Layout is always idiomatic stacks** (Ben's ruling, 2026-09-26): intent over pixel parity with Pen's flexbox, and no port of ``PenLayoutEngine``.

**Effects, transforms and blend modes** follow the renderer's rules (see <doc:PenRendering>, *Effects*), with `PenSupport+Effects.swift` supplying what SwiftUI lacks. A shadow's and a blur's SwiftUI `radius` is the Gaussian's sigma, half of Pen's `blur` or `radius`.

**Paints.** Every enabled fill is a layer, bottom to top, with its own `opacity` and blend mode; an opaque colour of normal blend hides the layers under it, which are left out. A layer is a `ShapeStyle` where SwiftUI has one, and a stack of styles keeps SwiftUI's idiom — the top one fills the shape, each lower one is a `.background(style, in: shape)`, and a fill's opacity and blend mode are the style's own `.opacity(_:)` and `.blendMode(_:)`:

```swift
Rectangle()
    .fill(.linearGradient(Gradient(stops: […]).colorSpace(.device), startPoint: .bottom, endPoint: .top).opacity(0.5))
    .background(Color(hex: 0x00FF00), in: .rect)
```

A layer that must be a view (an image, a `PenGradient`) makes every layer a view — a style fills a `Rectangle()` — in a `ZStack` clipped to the node; a frame with children takes that stack as one `.background { … }`. `linearBurn` and `linearDodge` are `.plusDarker` and `.plusLighter`, the same formulas.

- **Gradients** interpolate in device colour space, `Gradient(stops:).colorSpace(.device)`, as Pen and Core Graphics do; SwiftUI's default perceptual interpolation measured MAE 10.7 on `render-gradients`. Their geometry comes from `GradientGeometry`, Pen's map from the gradient's unit space into the normalised box, which is then stretched to the node. A **linear** gradient is `.linearGradient` with start and end points that keep Pen's stop lines: SwiftUI draws its stop lines square to the start–end line *in points*, so on an oblong box the end point is moved along stop 1's line (`SwiftUIGradient.linearPoints`) — exact whenever the box's size is fixed, and on any box when the gradient is turned by a multiple of 90°. A **radial** gradient of even `size` is `.ellipticalGradient(…, endRadiusFraction: size / 2)`, whose unit circle SwiftUI stretches to the box exactly as Pen does. An **angular** gradient is `.conicGradient(…, angle: .degrees(-90 − rotation))` when the whole map is a similarity (a square fixed box and an even size). Every other case — a turned or uneven radial ellipse, a conic on an oblong box, a turned linear gradient on a box sized at layout time — is the support file's `PenGradient(.kind, gradient, center:width:height:rotation:)`, a `Canvas` that draws through Pen's map itself. A stop's colour and position variables are each read through the theme; a stop naming a variable the document lacks is a warning and the gradient is not drawn.
- **Local images** (a path beside the .pen file) are `Image(penResource: "photo.png", bundle: .module)`, resizable, and `scaledToFill()` or `scaledToFit()` centred in a `Color.clear` overlay for `fill` and `fit`; the node's clip cuts a `fill` image, as Pen draws it. The support initializer loads the file from the bundle, because `Image(_:bundle:)` looks in asset catalogs and on macOS draws nothing for a loose file. ``EmitResult/imageAssetURLs`` lists every local image the pages use; `woodcase generate swiftui` copies each into `Sources/<Module>/Resources/`, which `Package.swift` always processes (*The manifest*, above). `.process` flattens resources, so two images with the same file name clash (a warning).
- **Remote images** (`http`/`https`, the same test ``RemoteImageResolver/isRemote(_:)`` makes for the Core Graphics renderer, <doc:PenRemoteImages>) are drawn live by SwiftUI's own `AsyncImage(url:)` instead of being bundled: the URL is fetched at *draw* time, on the device the generated package runs on, never at generate time — so `woodcase generate swiftui` needs no network, and the render test harness (which has none) never has to download anything either. The same resizable + `scaledToFill()`/`scaledToFit()` rule applies inside `AsyncImage`'s content closure, over the `Image` it hands in once loaded, and `fill`/`fit` centre the whole `AsyncImage` in a `Color.clear` overlay exactly as a bundled image's modes do. Nothing is shown while it loads or if it fails — `Color.clear`, as an image with no fill draws — though Pen itself draws a checkerboard placeholder for an image it cannot load (measured with `scripts/pen-oracle`, `project/2026-09-27-pen-missing-image-checkerboard.md`), a gap kept on purpose rather than built here (Ben's ruling D4, 2026-09-27: `AsyncImage` over bundling, `project/2026-09-27-fidelity-gaps.md`). An absolute filesystem path is still a warning and is not drawn: it names a file on the machine that generated the package, not one the running app can read.
- **Mesh gradients** are always drawn by SwiftUI's native `MeshGradient` (Ben's ruling, 2026-09-26: no baked raster in this emitter, folded meshes included), through the support file's `PenMeshGradient(columns:rows:points:colors:)`, a `ShapeStyle` like any gradient, so a mesh fills a shape, backs a frame, paints a stroke or shows through text. The grid is the renderer's ``PenMeshGrid``, so a mesh Pen would not draw (a missing field, a count that does not match the grid, a single row or column) writes nothing, and a malformed point sits where Pen places it. Each vertex is written as Pen saves it (``PenMeshPoint/canonicalized(defaults:)``): `[x, y]` when its handles are the grid's defaults, otherwise `PenMeshVertex([x, y], left: […], …)` with only the handles that differ, still relative, so the call reads like the .pen file. Handed Pen's grid directly, `MeshGradient` interpolates its own way, not Pen's bicubic patches and smoothstep-eased colours blended unpremultiplied, and measured MAE 0.4–3.2 on `render-mesh-gradients`' smooth boards, 5.0 on the translucent `malpha` and 7.1 on the folded `mfold`. So `PenMeshGradient` resolves (`resolve(in:)`, in the view's environment, so a colour that follows the environment moves the mesh) to a `MeshGradient` that splits each Pen cell into 8 × 8 cells, their corners, one-sided tangents and colours evaluated from Pen's own patch, drawn with `smoothsColors: true` in `.device` colour space over a clear background, so an uncovered part of the box stays bare as in Pen. That measures 0.18–0.83 on every board, the fold included, against the Core Graphics renderer's 0.24–0.38 (4 × 4 cells: 0.29–1.06; 16 × 16: 0.17–0.83). A fold still overdraws in SwiftUI's order rather than Pen's; `woodcase lint`'s `mesh-gradient-distorted` is the warning. A colour string is written as Pen's mesh reads it (``PenMeshColor/hexColor(penMesh:)``: a wrong length is clear, `red` is `#00EEDD`), as the renderer draws it. A colour variable is read through the theme (`theme.brand`), so the mesh follows the theme and the colour scheme at draw time; one the document does not declare is a warning and the mesh is not drawn. `MeshGradient` needs iOS 18 / macOS 15, the lower floor, so it takes no `#available` branch.

- **Text** of one plain colour keeps `.foregroundStyle(color)`. Text with no enabled fill is `.foregroundStyle(.clear)`: Pen draws it as nothing (measured on `swiftui-color-scheme.pen`'s `unfilled` board, 2026-09-27), where an unstyled `Text` would draw in `.primary`, black or white by the colour scheme; an icon with no fill is already `Color.clear`. The Core Graphics renderer draws it as nothing too (`PenUnfilledTextPaintTests`). Any other paint follows Pen, whose paint domain for text is the node's box: the layers go in the support file's `.penTextFill { … }` after the growth frame, which lays them over the text's box and shows them through its glyphs (`hidden()`, `overlay`, then `mask` by the text itself). A text with inner shadows always takes that path, one colour included, and a text with no paint gets `Color.clear` there, so its shadows still show: `.penTextFill(innerShadows:)` needs the glyphs unpainted to cast them. They are styled opaque black for it: an unstyled `Text` draws in `.primary`, which is black at 85 %, and cut out of the band it left a 15 % veil over the glyphs (measured with a probe build of `render-text-shadows`, 2026-09-27). The result is one compositing group, so the text's outer `.shadow` is cast once rather than by the paint and each inner shadow apart (6.46 before, 1.66 after on `text-inner-outer`).

**Text** is `Text("…")` — `Text(verbatim:)` when the copy holds characters Markdown would read — styled by the support file's `.penFont(family, size:weight:italic:lineHeight:)`, then `.tracking`, `.multilineTextAlignment`, `.foregroundStyle` and a frame per `textGrowth`: `.fixedSize()` for `auto`, which never wraps in Pen and would wrap as a flexible `Text` in a row too narrow for it; `.fixedSize(horizontal: false, vertical: true)` and the width for `fixed-width`; both axes, placed by `textAlignVertical`, for `fixed-width-height`. `penFont` pins optical sizing off, as Pen draws variable fonts (Core Text applies it automatically, which cost 0.44 MAE on `render-text` in the feasibility study), and sets the weight on a variable font's `wght` axis; on a static family it draws the cut CSS font matching picks for the weight, by each cut's OS/2 weight class (`PenSupport+FaceMatching.swift`, the renderer's ``PenFaceMatching`` rule) — a table of Core Text weight traits had drawn Medium as Regular and SemiBold as Medium (leaf `BpaSrF`). A `lineHeight` is placed the way Pen (and CSS) place it: each line box is `lineHeight × fontSize` rounded to a whole point tall and the difference from the font's ascent plus descent is split equally above and below the glyphs (half-leading), so the first baseline sits at `ascent + (lineHeight − ascent − descent) / 2`, rounded to a whole point — the rule the CG renderer follows. A text with no `lineHeight` is set at Pen's natural pitch, the font's ascent + descent + leading rounded to a whole point (``PenTextMeasurer/naturalLineHeight(of:)``, computed from the font at run time), its first baseline at the rounded ascent. SwiftUI's own natural pitch rounds the ascent and descent apart — Inter at 16 pt is 20 in SwiftUI and 19 in Pen, at 18 pt 21 and 22 — while its first baseline already sits where Pen's does (both measured on `text-natural-line-height.pen` against Pen's export). SwiftUI puts that space on one side — `lineHeight(.exact(points:))` sets the first baseline one em below the line's top whatever the height, measured 26 pt above Pen's on a 72 pt line at `lineHeight: 2` — so `penFont` wraps the text in the support file's `PenLineBox`, a `Layout` that reads the text's reported `firstTextBaseline` and moves it to Pen's. The box is also the text's size rounded up to whole points, as ``PenTextMeasurer`` measures a text node for Pen's layout: SwiftUI's own size is fractional, so a `fit_content` frame around a text was a fraction of a point narrower than Pen's (a pixel at 2x: `codegen-states`' chip rendered 137 pixels wide against Pen's 138), and an `auto` label centred in a fixed button sat half a pixel off. It wraps every branch, the pre-iOS 26 natural pitch included, where it leaves the baseline where SwiftUI sets it. Before iOS 26 the text has only `lineSpacing`, which cannot be negative: the box adds the first line's share, which makes every line box exact when lines are looser than the font's own, and only the first when they are tighter (later lines keep the font's own height there); a text with no line height keeps SwiftUI's natural pitch there. `textAlign: justify` has no SwiftUI equivalent; it is drawn leading, with a warning.

**Strokes** follow the renderer (see <doc:PenRendering>): a stroke is painted like a fill — every paint a fill can carry, stacked, with its opacity and blend mode — laid out over the node's box, through the region the stroke covers. It is drawn in Pen's paint order: outer shadows, fills, inner shadows, **stroke**, children. On a shape it is an `.overlay` after the `.penInnerShadow`s; on a frame with children, a `.background` placed over the inner shadow and under the children. `PenSupport+Stroke.swift` supplies what SwiftUI lacks.

| Pen | SwiftUI |
|---|---|
| a centred stroke of one paint | `shape.stroke(paint, lineWidth: w)`, SwiftUI's own |
| an inner stroke of one paint on a box whose rounded corners are all at least `w / 2` | `shape.strokeBorder(paint, lineWidth: w)`, which then draws exactly Pen's band |
| any other alignment, shape or stack | `shape.penStroke(.inside / .center / .outside, lineWidth: w)` — the outline stroked (at twice the width, cut to the shape or its complement, for inside and outside), a `Shape` filled like the node's outline: `.fill(top)`, `.background(lower, in: region)`, or a `ZStack` of views clipped to it |
| `strokeLinecap`, `strokeLinejoin` | `style: StrokeStyle(lineWidth:lineCap:lineJoin:)`, only when not butt and mitre — SwiftUI's defaults, and Pen's |
| per-side `strokeWidth` on a box | `PenSideStroke(EdgeInsets(…), alignment:, cornerRadii:)`: the renderer's outer rounded rectangle less an inner one, with elliptical inner corners; on a box under a point on an axis, `.penOutset(dx:dy:)` after it |
| per-side `strokeWidth` on any other shape | the uniform stroke of its `top` width above, as Pen draws it (``PenStrokable/drawn(on:)``, <doc:PenRendering>); none when there is no `top` |

A gradient drawn as a view (`PenGradient`) is given room past the box with `.penPaintBleed(_:)` — the reach of a centred or outer stroke, at the mitre limit — because Pen pads a stroke's gradient beyond the box; an image stroke draws only where the image is placed. A uniform or per-side width that names a variable reads the theme's number; one the document lacks is a warning and draws no stroke. The .pen format has no dash key, so there is none to write.

**Shapes.** A path, polygon, line, arc or donut is a `Shape` the page declares below its view, `private struct <Name>Shape: Shape`, named for the node and made unique on the page. Its `path(in:)` writes `PenShapeGeometry`'s outline — the one the renderer draws — as the `Path` calls of the same names (`move`, `addLine`, `addQuadCurve`, `addCurve`, `addArc(tangent1End:…)` for a rounded polygon's corners, `addArc(center:…transform:)` for an arc, `addEllipse`), at the node's size, and fits it to the box it is offered with the support file's `penFitted(from:to:)`. A path's `viewBox` or tight bounds, a polygon's first vertex at the top and an arc's angles are all decided there. An even-odd shape — a path that declares it, a ring — is filled, backed and clipped with `FillStyle(eoFill: true)`. A plain ellipse stays `Ellipse()`. SwiftUI draws no view under a point on either axis — not its stroke, not its overlay — so a stroke on a box that flat (every axis-aligned line) is drawn with the support file's `penOutset(dx:dy:)`, the shape inset in the box it is offered, and `.padding` of minus the stroke's width (at least a point) on each flat axis: the stroke's view has room to draw, the line sits where it was, and the node's layout box stays Pen's.

**Icons** are `PenIconShape(file: "lucide.ttf", glyph: 0xE176)`: the glyph's outline read with Core Text from the library's font, registered with the package's other fonts (`PenFonts`, *Fonts* above), as tall as the box's shorter side and placed as Pen places it — its advance centred across the box and its line box centred down it, by the renderer's rule (see <doc:PenIconFonts>), a `Shape` painted with the node's fills like any other. A Material Symbols icon passes its `weight:` (Pen's default 200 when unset) to the font's `wght` axis. An unknown name draws the library's own question mark, as Pen does; a library with no bundled font is a placeholder with a warning. ``EmitResult/iconLibraries`` names the libraries the pages draw from, and `woodcase generate swiftui` copies each one's font (``SwiftUIEmitter/iconFontFiles(for:)``) into `Sources/<Module>/Resources/`.

**Components and instances.** Each reusable component the analyzer finds is a `public struct <Name>: View` under `Components/`, named as React names it — `ToggleView` where the name would shadow a SwiftUI type or a type the support files declare (read from the templates, `SwiftUIEmitter.supportTypeNames`), numbered where two components share one; a page that shares a component's name is suffixed `Page`. Each `_props` entry the body can read is a `public let` and a parameter of a public init whose default is what the component draws:

```swift
public struct Card: View {
    public let label: String

    public init(label: String = "Total") {
        self.label = label
    }

    public var body: some View { … Text(label) … }
}
```

| Prop | Swift type | Read by |
|---|---|---|
| text (a `text` node's content) | `String` | the node's `Text(label)`, verbatim |
| colour (a node whose first paint is a solid colour) | `Color`; `Color? = nil` when the paint is a variable | that paint layer; `tint ?? theme.accent` when optional |
| image (a node whose first paint is a local image) | `Image` | that layer, resizable and placed by the fill's mode |

An image prop's parameter is `Image? = nil`, its default (`Image(penResource: "photo.png", bundle: .module)`) applied in the init's body, because SwiftPM's `Bundle.module` is internal and a public init's default argument may not name it; `Color(hex:)` and `Image(penResource:bundle:)` are public in the support files so a caller can pass either. A prop the body cannot read (a text prop on a frame, a path that names nothing) is left out with a warning. A component's root is sized as its instances are placed: `fill_container` takes whatever the caller offers. A component with a role or states is written as the control its role becomes (*Roles and states*, below).

An instance (a `ref`) is a call — `Card(label: "Revenue")`, with arguments only for props that differ from the default — when that call draws what Pen does: the component is one the module declares; every override is either carried by a prop or changes nothing (`InstanceOverrides`, target-neutral: an `x`/`y` on a node its parent lays out, a value equal to the node's own, a size that sizes the node as it already was); the instance is not turned or flipped; and the component's root sizes the same where the instance sits as in its own body. Otherwise the instance is **inlined**: the copy ``PenRefExpander`` prepares, with every override Pen applies — paths into nested instances, slot content, alias chains — under a `// woodcase: inlined from <Name>` comment, with a warning naming what no prop carries; the instances inside it are calls or copies in turn. A root size override inlines, because a `.frame` on the call site cannot resize a view that frames itself. An instance that fills a slot is a call with trailing closures (*Slots*, below). A `ref` to nothing, or to a component inside itself, is a placeholder with a warning. The images, icon libraries and text families ``EmitResult`` lists are read from every page and component with its instances expanded, groups included, so an image or a family only an override names is bundled too. See `project/2026-09-26-swiftui-components.md` for the design choices.

**Slots.** A frame of the component's own tree marked `slot` is a `@ViewBuilder` parameter: one generic parameter per slot, named for the frame with `Content` after it (`Content` for a frame named "Content", `HeaderContent` for "Header"; `Body` is `View`'s), a `private let` the slot frame's stack draws where Pen draws the frame's children, and an init parameter that builds it. The frame's own children are the slot's **default content**, a view of their own — `CardContentDefault`, top level, since a type nested in a generic struct could not name itself in the struct's own constraint — and a constrained init passes each slot its default, so `Card()` and the preview draw what Pen draws; a slot without children defaults to `EmptyView`:

```swift
public struct Card<Content: View>: View {
    public let title: String
    private let content: Content

    public init(title: String = "Card title", @ViewBuilder content: () -> Content) { … }
    public var body: some View { … VStack(alignment: .leading, spacing: 8) { content } … }
}

extension Card where Content == CardContentDefault {
    public init(title: String = "Card title") {
        self.init(title: title, content: { CardContentDefault() })
    }
}
```

An instance that fills a slot (a `children` override of the slot frame, with nothing else on it that no prop carries) is a call with trailing closures — the first slot's unlabelled, the rest labelled by the slot's name — holding the instance's content, drawn in the caller's scope as the slot frame's stack places children; a slot the instance leaves alone passes its default (`} footer: { PanelFooterDefault() }`), and an instance that fills none is a plain call through the constrained init. A slot's name avoids the props' and the control's members (`titleContent` beside a `title` prop); a control's slot parameters follow its members, and its constrained init forwards them. A prop read inside a slot's default content is left out with a warning: a caller's content replaces the node it names. Two slot frames are drawn as plain frames, with a warning, and an instance that fills one is inlined: a frame that spreads its children with `space_between` or `space_around` (the spacers go between the children; a caller's content is one view), and one whose default content places a child absolutely in a stack (that child rides in the frame's overlay). A fill that places a child absolutely in a stacked slot is inlined for the same reason. `codegen-slots.pen` is the fixture; its components and pages are golden-pinned, built, and rendered against Pen's exports (`SwiftUISlotRenderTests`).

**Themes.** The document's theme axes and variables (``ThemeAnalyzer``) are `Theme/PenTheme.swift`: a `public struct PenTheme` with one enum per axis (`enum Mode: String { case light, dark }`) and a stored property for each, defaulting to the axis's first option as Pen's default theme does, and one computed property per variable — `Color`, `CGFloat`, `String` or `Bool` — that switches on only the axes its value varies along:

```swift
public extension PenTheme {
    /// `$bg-page`.
    var bgPage: Color {
        switch mode {
        case .light: Color(hex: 0xFAF8F4)
        case .dark: Color(hex: 0x1A1A1A)
        }
    }
}
```

Each variable is evaluated under every combination of options with the renderer's own rule (`PenVariableResolver`: a specific match before the unconditional default, the last match winning, chains followed), so a property reads exactly what Pen draws under each theme; two axes are a `switch (contrast, mode)` over every pair. A variable that has no value of its type under some theme is left out with a warning. `Theme/PenTheme+Environment.swift` carries the value as `EnvironmentValues.penTheme`. A view whose body reads a variable declares `@Environment(\.penTheme) private var theme` and writes `theme.bgPage` wherever the number or colour goes: fills and strokes, gradient stop colours and positions, shadow colours and geometry (blur, offset), layer and background blur radii, rotation, text colour and content, font family and size, line height, letter spacing, gap, padding, corner radius, a uniform or per-side stroke width and opacity. A rotation variable's turn is `.rotationEffect(.degrees(-theme.angle))` as a literal's is; where a fixed-size stack child would otherwise be framed to its exact rotated bounding box (*Layout is always idiomatic stacks*, above), a themed rotation writes that box's trigonometry as an expression instead of a literal, read at draw time, since the angle is no longer known when the code is generated — `cos`, `sin` and `abs` resolve under the page's own `import SwiftUI`. Sizes that name variables are still warnings. A text's `$name` that names no variable is the literal it was (`$186`), as the resolver reads it.

A node with a `theme` — a context node — is `.penTheme(mode: .dark)`, a generated modifier with one optional parameter per axis that sets the axes it names for the node's subtree. A view's `theme` property reads the environment around the view, so a context node whose own paints or children read the theme in the same body is wrapped in `PenThemeReader { theme in … }`, which hands its content the theme the modifier set. An instance with a `theme` is the call under the modifier (`Ratings().penTheme(mode: .dark)`), and a variable passed to a prop is the caller's read (`Swatch(tint: theme.ink)`). When an axis's options are `light` and `dark`, that axis *is* the colour scheme: `penTheme` reads it from `colorScheme` and setting it sets `colorScheme`, so an app in dark mode draws the dark theme unasked, `.preferredColorScheme(.dark)` selects it, and `.penTheme(mode: .dark)` darkens SwiftUI's own controls and materials in the subtree too. Another axis (banking's `scheme: day/night`) is carried as it is. See `project/2026-09-27-swiftui-themes.md` for the design choices.

**Roles and states.** A component with a `_role` on its root, or with states, is written as the SwiftUI control its role becomes, wrapped around its drawing:

| Role | SwiftUI | Added to the struct |
|---|---|---|
| `button`, `link` | `Button(action:)` drawn by a nested `ButtonStyle` | `action: () -> Void = {}` |
| `toggle` | `Toggle(isOn:)` drawn by a nested `ToggleStyle`, which toggles on a tap | `@Binding isOn`, defaulting to `.constant(true)`: the component's frame is the on state, as React's `checked = true` |
| `textInput` | the component with its first text drawn as a plain `TextField`, the copy its prompt, in the text's colour | `@Binding text` (`.constant("")`) and a `@FocusState` |
| `select` | a `Menu` holding an inline `Picker` over `options`, its label the component, drawn by a nested `ButtonStyle` | `@Binding selection` (`.constant("")`), `options: [String] = []` |
| `tabBar` | the bar drawn for its `selected` tab, `.accessibilityAddTraits(.isTabBar)` | `selected: Tab? = nil`, an enum of its variants |
| none, with `_states` | the component drawn for its `variant` | `variant: Variant? = nil` |

The drawing is a private `face` property; each state the designer drew (a `{Name}:{state}` sibling or a `_states` frame) is another, `pressedFace`, drawn from the designer's whole frame with the component's props bound where the same paths lead, so a pressed button's label still reads `label`. `PenStateReader` (in `PenSupport+States.swift`) reads which interactions hold — `.onHover`, the style's `isPressed`, `isFocused`, `isEnabled` — as a `PenControlState` and draws the first face whose state holds: disabled, then pressed, hovered, focused, then the attribute states; the smart defaults of the states the designer did not draw are modifiers on top. An attribute state is read from the control that reports it (a toggle's `on` and `off` from `isOn`, a text input's `filled` from `text`) and is otherwise a case of the `Variant` (or `Tab`) enum the caller sets — a select's `open`, which no `Menu` reports, among them. A text input's designer-drawn `focused` and `filled` states are drawn as their smart default, with a warning: swapping the frame while the field is typed into would make a new `TextField` and drop the focus. Every state gets a preview that pins it — `.penControlState(.pressed)` (public in the support file, for any preview or snapshot), `.disabled(true)`, `isOn: .constant(false)`, `variant: .open`. Each is repeated under every other theme option (*Previews and the catalog*, above), and the catalog draws them side by side. An inlined copy of a role component draws its default face without the control. See `project/2026-09-27-swiftui-roles-and-states.md` for the design choices.

**The deployment floor** is ``SwiftUIEmitter/DeploymentFloor``: iOS 26 / macOS 26 by default, or iOS 18 / macOS 15. View code is written for 26 and is byte-identical at every floor; the lower floor is served only by `#available` branches in the support files (today one, in `PenSupport.swift`: `lineHeight(.exact(points:))`, which falls back to `lineSpacing` and a taller `PenLineBox` before 26, and to SwiftUI's own pitch for a text with no line height), so the floor changes the manifest's platforms and nothing else. The support files are bundled resources in `CodeGen/SwiftUITemplates/`, copied verbatim: `PenSupport.swift` is the core, and each concern that needs helpers (paints, effects, strokes, shapes, line height) adds its own `PenSupport+<Concern>.swift` there, which the emitter picks up by being in the directory.

**The library never imports SwiftUI.** The emitter is Foundation-only string generation; SwiftUI appears only in the text it writes. `SwiftUIEmitterIsolationTests` scans `CodeGen/SwiftUI/` for UI and graphics imports, which stands in for a Linux build until the library builds there.

Both renderers now place those lines by one rule — the pitch rounded to a whole point per line, the glyphs centred in it by half-leading with the baseline on a whole point (``PenTextMeasurer/linePitch(lineHeight:fontSize:font:)``, ``PenTextMeasurer/firstBaseline(of:lineHeight:pitch:)``) — and SwiftUI matches CG to the thousandth on four of the five (`fixed-middle` 0.79 against CG's 0.07), so they gate at CG + 1.0 (measured 2026-09-27, leaf `HVBKsf`, `swift test -j 3 --filter SwiftUIRenderTests`). Before, the CG side left the placement to Core Text and Inter's optical size to the point size, scoring 5.5–13.4, and the boards were held to ceilings of their SwiftUI MAE + 0.5. Strokes and shapes (measured 2026-09-26, same command): the 26 `render-per-side-strokes` boards 0.000–0.031 (CG 0.000–0.027), the 25 `render-stroke-fills` boards 0.000–0.065 (CG 0.000–0.071), the 5 `render-arc-donut` boards 0.032–0.218 (CG 0.049–0.127), the 10 `render-fill-domains` boards 0.037–0.151 (CG 0.026–0.132), the 8 `render-mesh-gradients` boards 0.181–0.825 (CG 0.235–0.380: `malpha` 0.181, `mfold` 0.825, the rest 0.447–0.462), `render-strokes-and-paths` 0.034 (CG 0.027, against a reference re-exported with `scripts/pen-oracle`; both scored 5.1 against the older export it replaced) and `parser-icon-font` against Pen's `icon-font-test.png` 0.84 (CG 1.24; 4.73 and 5.25 before icons were placed by the font's metrics, leaf `VMKixs`, 2026-09-27), all gated at CG + 1.0; the widest gap over CG is `outer-and-inner`'s 0.37. Text inner shadows (leaf `vVgtB2`, measured 2026-09-27 with `swift test --filter "SwiftUIRenderTests|PenTextShadowSnapshotTests"`): the six `render-text-shadows` boards — an offset shadow, a soft centred one, a white inner highlight under an outer shadow, wrapped lines, an unfilled text and a quarter-transparent one — measure `text-inner` 0.556 (CG 1.363), `text-inner-soft` 0.615 (1.045), `text-inner-outer` 1.657 (1.293), `text-inner-wrap` 2.027 (2.013), `text-inner-unfilled` 1.024 (1.767) and `text-inner-translucent` 0.717 (1.370), all gated at CG + 1.0; before, SwiftUI dropped them with a warning. Inner shadows on shapes and icons, and painted flat lines (leaf `4fZZ38`, measured 2026-09-28 with `swift test -j 3 --filter SwiftUIRenderTests`): the `render-inner-shadow-shapes` and `render-painted-lines` boards (`effectProbeBoards`) measure 0.010–0.357, each within CG + 1.0; the donut (now 0.357) measured 19.898 until its inner shadow was clipped even-odd, and `render-painted-lines-fill-degenerate` measures 16.255 against CG's 16.297, the kept divergence of a ramp across a flat line (<doc:PenInteroperability>).

Components and pages have goldens of their own: every file under `Components/` and `Pages/` that `woodcase-app.pen`, `pages.pen` and `codegen-states.pen` emit, one golden per file under `golden/swiftui/<fixture>/`, with an `index` of the files (`SwiftUIEmitterComponentGoldenTests`; rewrite with `UPDATE_GOLDEN=1 swift test --filter SwiftUIEmitterComponentGoldenTests`). `SwiftUIScreenRenderTests` emits `woodcase-app.pen` as it is, variables unresolved, with each top-level instance Pen exported a screen through (`Ratings (Light)`, `Ratings (Dark)`, `Settings (Compact)`…) passed as a page, so each screen is drawn exactly as the emitter writes that instance — a call under its theme. It compiles every component, page and the theme at the default floor and type-checks them at macOS 15, renders the fourteen screens and records each one's MAE against Pen's `woodcase-app-*.png` as a baseline. `SwiftUIStateRenderTests` compiles `codegen-states.pen`'s components — a button with pressed, disabled and hover frames, a switch with an off frame, a text field, a select with an open frame, a link and a role-less chip with a `_states` frame — at both floors, renders each in every state a caller can pin, and records its MAE against Pen's export of the matching `:state` sibling frame (`scripts/pen-oracle`, 2x). Measured 2026-09-27 (`swift test --filter SwiftUIStateRenderTests`, Xcode 27.0, macOS 27.0): the button 0.96, pressed 1.05, disabled 0.67, hover 0.82; the switch 0.89 and off 0.88; the select 0.89 and open 0.59; the chip 2.70 and selected 4.15; the link 5.01. The error is the text, not the state. Before `PenLineBox` rounded a text's size up to whole points, the `fit_content` chip and link rendered a pixel narrower than Pen's at 2x and the button's centred label half a pixel off (the chip 3.13, selected 4.68, the link 5.96, the button 2.38–2.64); the test now also requires each render to be the reference's size. What is left on the chip and the link is Core Text's glyphs themselves, which cover more than Pen's — on the link's transparent board the mean alpha is 41.7 against Pen's 34.7 — and the Core Graphics renderer scores the same three boards 2.57, 4.09 and 4.98 (`woodcase shot codegen-states.pen <id> --scale 2`, then `scripts/png-mae`). The text field is compiled but not rendered: `ImageRenderer` draws a platform-backed `TextField` as a placeholder symbol.

`SwiftUIThemedNumbersRenderTests` measures the four kinds of number the theme reads outside a colour — a shadow's blur, a rotation, a gradient stop's position and a per-side stroke width — on `render-themed-numbers`'s light and dark boards, each built by `SwiftUIThemedNumbersBatch` in a compile of its own: the shared `SwiftUIRenderBatch` holds one `PenTheme` for the whole run, and `swiftui-color-scheme` already claims that slot ("two themed fixtures must agree on it"). Measured 2026-09-27 (`swift test --filter SwiftUIThemedNumbersRenderTests`, Xcode 27.0, macOS 27.0, 2x references): light 0.535 (CG 0.819), dark 0.637 (CG 1.922), both gated at CG + 1.0 — the dark board's rotated rectangle turns through a runtime `cos`/`sin` expression rather than a literal, since the angle is no longer known when the code is generated.
